Important correction:
Do not describe this as “full Codex-style behavior” yet. This task should be named:

Orax Agentic Loop Phase 1 — Inline Agentic Context Selection + Natural Plan Mode

The goal is not only to make Orax look like Codex. Orax must work inline like a Codex-style agentic coding assistant.

Orax should not feel like a dashboard, workflow panel, or form-based tool. The user should experience everything inside the chat thread:

user request → Orax understands → Orax selects context → Orax inspects files → Orax plans → Orax asks approval only when needed → Orax continues inline → Orax implements → Orax checks → Orax fixes failures → Orax summarizes → Orax offers PR.

Everything should happen inline in the Orax conversation, similar to Codex.

The inline chat should feel like an agentic AI software engineer that understands the project, the repository, the current task, the previous steps, the files, the plan, the approvals, the checks, and the next action. This is not only a UI/style task. It is functionality, workflow, behavior, and quality.

Do not copy OpenAI branding or proprietary implementation. The goal is functional equivalence under MustaFlow AI/Orax architecture and branding.

Do not touch Ora.

Absolutely do not modify:
- Ora chat
- public-ai routes
- AI Builder
- project chat
- credits
- billing
- unrelated mobile screens

Required changes:

1. Everything must happen inline, like Codex

The normal Orax experience should be the chat thread.

Do not bring back:
- dashboard workflow panels
- visible artifact IDs
- visible approval IDs
- checkpoint spam
- status dump messages
- separate “workflow controls” as the main experience
- manual step-by-step control panels

Good inline behavior:
- “Inspecting files”
- “Reading package.json”
- “Planning the change”
- “Preparing changes”
- “Running checks”
- “Fixing failure”
- “Ready for review”
- “Create pull request”

Bad behavior:
- “Current task status”
- “Approvals: 0”
- “Artifacts: 0”
- “Phase 4B”
- raw approval IDs
- raw artifact IDs
- large workflow reports
- user needing to manually choose every internal operation

The user should talk naturally, and Orax should continue the engineering workflow inline.

2. Domain-aware file inference must be repo-scan aware

Do not only return hardcoded file names.

Implement:
- inferOraxDomainPaths(prompt, repositoryScanSummary/tree)
- Use the latest repository scan file tree if available.
- Score real files from the repo tree based on prompt/domain.
- Prefer actual matching files over imaginary canonical paths.
- Fall back to canonical guesses only when the scan is missing or weak.

Examples:
- login/auth prompt:
  Prefer real files containing auth, login, session, clerk, middleware, user, account.
  Also include package.json and relevant route/layout files if present.
- mobile/layout prompt:
  Prefer app screens, navigation files, component files, styles/theme files.
- build/test/typecheck failure:
  Prefer package.json, tsconfig, vite/expo config, test config, lockfile, relevant source entry points.
- repo explanation:
  Prefer README, package.json, app/router entry points, database/schema files, main backend/frontend entry points.
- UI screenshot/layout issue:
  Prefer screens/components/style/theme/layout files.

3. Merge inferred files correctly

Inside requestOraxRunnerFileReadApproval:
- combine:
  - literal paths from extractOraxCandidatePaths
  - domain-inferred paths from repository scan
  - attachment-detected paths
  - task kind hints
- deduplicate
- cap to ORAX_FILE_READ_LIMITS.maxFiles
- keep best-ranked files first
- never ask the user “what files should I read?” if there is enough confidence to propose a useful file-read approval.

Orax should feel like it knows what to inspect, similar to Codex.

4. Natural-language plan mode must work outside /plan

Extend plan detection so these trigger plan-first behavior:
- “plan this first”
- “make a plan first”
- “think before implementing”
- “outline the approach”
- “show me the plan”
- “plan only”
- “no changes yet”
- “analyze before changing”
- “review first then plan”

These should behave like /plan:
- inspect context
- generate a plan
- stop before patch/edit
- wait for “continue” / “start implementation”

But normal implementation prompts should not accidentally become plan-only:
- “fix the bug”
- “change the button”
- “run the tests”
- “create PR”

Those should stay normal execution unless plan intent is clear.

5. Inline agentic memory and task awareness

Orax should use the current task thread as working memory.

It should know:
- what the user asked
- what repository is connected
- what files were inspected
- what plan was created
- what approvals are pending
- what checks ran
- what failed
- what the next action is

When the user says:
- “continue”
- “go ahead”
- “what happened?”
- “what is next?”
- “fix it”
- “run checks”
- “create PR”

Orax should understand the current task state and continue inline, not restart or show unrelated controls.

6. Plan mode behavior

In plan mode:
- inspect context
- produce a clear implementation plan inline
- stop before edits
- show inline “Start implementation” / “Continue”
- after continue, proceed into implementation

In normal mode:
- inspect context
- plan briefly if needed
- continue implementation if safe
- stop only for approval, missing context, or user decision
