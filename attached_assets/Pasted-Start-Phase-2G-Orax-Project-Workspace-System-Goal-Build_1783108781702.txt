Start Phase 2G — Orax Project Workspace System

Goal

Build the real Orax Project system. Do not treat “project” as only a local folder picker. An Orax Project is the durable workspace container that holds threads, attached execution sources, desktop hosts, GitHub repos, local folders, settings, permissions, usage history, and mobile sync.

This phase should make Orax behave closer to Codex: users create/select a project, then start coding threads inside that project. The project may later attach a local folder, GitHub repo, worktree, cloud env, or SSH host. Mobile should mirror the same projects/threads and remote-control the connected desktop host.

Do not touch Ora, public-ai chat, AI Builder, credits, or normal project chat. Only Orax / Orax Desktop / Orax mobile / Orax backend.

Core Product Model

Use this hierarchy:

Orax Project
- Durable cloud workspace owned by userId.
- Exists even before a folder is attached.
- Contains project name, description, status, optional icon/color, createdAt, updatedAt.
- Contains project memory/settings/instructions.
- Has many Orax threads.
- Has zero or more execution sources.

Orax Thread
- Conversation/task inside an Orax Project.
- Can run locally, in worktree mode, or later cloud/SSH mode.
- Stores messages, approvals, actions, diffs, results, summaries.

Desktop Host
- A signed-in Orax Desktop install.
- Provides local execution, PowerShell/terminal, Git, files, credentials, sandbox, permissions.
- Can be paired to web/mobile.
- Can have multiple local project folders.

Execution Source
- A project attachment that can be used as context/execution target.
- Types:
  - local_folder
  - github_repo
  - worktree
  - cloud_env (future)
  - ssh_host (future)
- A project can exist without one, but real coding execution requires at least one active execution source.

Local `.orax/`
- When a local folder is attached, create/use a `.orax/` folder inside that project folder.
- This stores local project config, not user secrets.
- Suggested files:
  - `.orax/project.json`
  - `.orax/local-env.json`
  - `.orax/actions.json`
  - `.orax/cache/scan-summary.json`
- Do not put tokens, private keys, or secrets in `.orax/`.

Important Behavior

A user can:
1. Create a new Orax Project from website, desktop, or mobile.
2. Name/rename/archive/delete the project.
3. Start a chat/thread inside the project.
4. Attach a local folder from Orax Desktop.
5. Attach a GitHub repo from website/desktop.
6. See the same project and thread list on website, desktop, and mobile.
7. Install Orax on a new laptop, sign in, and see their cloud projects.
8. For projects with missing local folders on the new laptop, show “Reconnect folder” or “Clone from GitHub”.
9. Mobile can choose a project, see active desktop host status, continue a thread, approve actions, and review outputs.

Recommended DB Changes

Use or extend existing Phase 2B tables carefully.

Add or update tables as needed:

1. orax_projects
Fields:
- id
- userId not null
- name not null
- description nullable
- icon nullable
- color nullable
- status: active | archived
- defaultExecutionSourceId nullable
- memory jsonb default {}
- settings jsonb default {}
- createdAt
- updatedAt

2. orax_project_sources
New table if current schema does not support multiple sources cleanly.
Fields:
- id
- projectId not null
- userId not null
- hostId nullable
- type: local_folder | github_repo | worktree | cloud_env | ssh_host
- displayName not null
- localPath nullable
- repoUrl nullable
- branch nullable
- worktreePath nullable
- status: active | missing | disconnected | archived
- metadata jsonb default {}
- lastSeenAt nullable
- createdAt
- updatedAt

3. orax_threads
Ensure it has:
- projectId nullable or not null depending migration safety
- userId
- hostId nullable
- executionSourceId nullable
- title
- status
- mode: local | worktree | cloud | ssh | chat_only
- createdAt
- updatedAt

4. orax_thread_messages
Ensure messages belong to threadId and remain separate from Ora messages.

5. orax_audit_log / orax_usage_events
Include projectId and executionSourceId where relevant if missing.

Backend API Requirements

Add/verify these Orax-only endpoints:

Projects:
- GET /api/orax/projects
- POST /api/orax/projects
- GET /api/orax/projects/:projectId
- PATCH /api/orax/projects/:projectId
- DELETE or POST /api/orax/projects/:projectId/archive

Project sources:
- GET /api/orax/projects/:projectId/sources
- POST /api/orax/projects/:projectId/sources/local-folder
- POST /api/orax/projects/:projectId/sources/github
- PATCH /api/orax/projects/:projectId/sources/:sourceId
- DELETE or archive /api/orax/projects/:projectId/sources/:sourceId

Threads:
- GET /api/orax/projects/:projectId/threads
- POST /api/orax/projects/:projectId/threads
- PATCH /api/orax/threads/:threadId
- POST /api/orax/threads/:threadId/archive

Desktop host/local folder:
- Desktop should register local folders as project sources.
- Desktop should create/read `.orax/project.json`.
- Desktop should report missing local paths as source status = missing.
- Desktop should not silently execute if the source is missing.

Security Requirements

- Every query must be scoped by userId.
- Cross-account project/source/thread access must return 404 or 403.
- Local folder paths must never be exposed to other users.
- `.orax/` must never store tokens or secrets.
- If a project source is missing, Orax must not run commands against fallback cwd.
- Mobile can approve actions only for projects/threads owned by the signed-in user.
- Keep Ora isolated. No imports from Ora chat routes/components/state.

Desktop App Requirements

In artifacts/orax-desktop:

1. Add Projects page behavior:
- Show cloud projects after login.
- Allow create project.
- Allow select project.
- Allow attach local folder to selected project.
- When attaching folder:
  - create `.orax/` if missing
  - write `.orax/project.json`
  - register source with backend
  - run lightweight scan/metadata
- Show missing/reconnect state if path is unavailable.

2. Sidebar:
- Projects list.
- Active project.
- Settings.
- Connections/pairing.
- Help/support.

3. Thread start:
- New thread requires selected project.
- If project has no execution source, allow chat-only planning but show “Attach folder or GitHub repo to execute”.
- If source is attached, thread can use local/worktree execution.

Website Requirements

In mustaflow Orax surfaces:

1. Orax card:
- If no desktop host: route to product/download/connect flow.
- If desktop host exists but no projects: route to project creation.
- If projects exist: route to Orax project list/workspace.

2. Orax workspace:
- Project list.
- Create project.
- Rename/archive project.
- Show connected desktop hosts.
- Show project sources: local folder, GitHub repo, worktree.
- Show missing source state with “Reconnect on desktop” or “Clone from GitHub”.
- Start thread inside project.
- Thread UI remains inline, not dashboard-heavy.

Mobile Requirements

In ora-mobile Orax:

1. Mobile should mirror projects:
- Project list.
- Active host status.
- Threads under each project.
- Start/continue thread.
- Show “Desktop offline” if host unavailable.
- Show “Reconnect folder on desktop” if source missing.
- Mobile must not pretend it can execute without an online host/source.

2. Mobile remote-control behavior:
- User sends prompt from mobile.
- Thread runs on connected desktop host when online.
- Mobile receives progress, approvals, command outputs, summaries.
- Same thread remains available on website/desktop/mobile.

Project Memory / Instructions

Add project-level memory/settings field:
- project summary
- repo/framework notes
- setup commands
- test commands
- preferred package manager
- known scripts
- coding instructions
- permission defaults

This should be used later by the agentic runner, but Phase 2G should at least store and retrieve it.

Definition of Done

Phase 2G is complete only when:

- User can create an Orax Project.
- Project syncs across website, desktop, and mobile.
- Desktop can attach a local folder to a project.
- `.orax/project.json` is created locally.
- Website/mobile show project/source/host status.
- Threads are created inside projects.
- Orax refuses execution when no active execution source exists.
- Missing local folders are shown as reconnect-needed, not silently ignored.
- Ora remains untouched.
- All verification commands pass.
