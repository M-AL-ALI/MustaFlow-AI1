NEW TASK: Optimize Talk to Ora Focused mode latency + investigate mid-speech glitches

Current state:
Focused mode is working better and background-speaker rejection is improved. Do not remove Focused mode. Do not go back to server auto-response for Focused mode.

Problem:
Ora now takes longer to reply, and sometimes speech/playback feels glitchy in the middle.

Likely cause:
Focused mode uses client-owned response creation:
speech detected → finalized transcript → focus scorer → response.create.

This adds latency compared with server auto-response.

Required investigation:

1. Add realtime latency diagnostics.

In website realtime hook and mobile realtime hook, log privacy-safe timestamps/durations for:

- speech_started
- speech_stopped
- transcript_completed
- transcript_accepted
- transcript_rejected
- response_create_sent
- response.created
- output_audio_buffer.started
- output_audio_buffer.stopped
- output_audio_buffer.cleared
- response.done
- assistant_cancelled_for_barge_in

Do not log raw audio.
Avoid raw transcript logging in production.
It is okay to log transcript length, focus mode, accepted/rejected reason, and timing deltas.

Needed timing metrics:
- speech_stopped → transcript_completed
- transcript_completed → response_create_sent
- response_create_sent → response.created
- response.created → output_audio_buffer.started
- output_audio_buffer.started → output_audio_buffer.stopped
- output_audio_buffer.stopped → response.done
- number of output stopped/started cycles per reply

2. Identify which delay bucket is slow.

If speech_stopped → transcript_completed is slow:
The bottleneck is VAD/transcription finalization.

If transcript_completed → response_create_sent is slow:
The bottleneck is client focus scoring / event handling.

If response_create_sent → output_audio_buffer.started is slow:
The bottleneck is model/realtime response generation.

If output_audio_buffer.started/stopped repeats during one reply:
The glitch is playback/buffer/event-state handling.

3. Optimize Focused mode latency without reopening background-speaker bug.

Possible safe improvements:

A. Tune VAD settings.

Current backend default uses semantic_vad with low eagerness.
Test whether medium eagerness improves response time without increasing background-speaker false accepts.

Environment knobs:
- ORA_REALTIME_VAD_TYPE
- ORA_REALTIME_VAD_EAGERNESS
- ORA_REALTIME_VAD_THRESHOLD
- ORA_REALTIME_VAD_SILENCE_DURATION_MS

Do not blindly change production defaults. Test on website first.

B. Consider a faster focused-mode response trigger.

Currently response.create waits for finalized transcript acceptance.
Investigate whether it is safe to send response.create immediately after transcript acceptance, and whether acceptance can happen earlier from partial transcript only when:
- focus window is active, or
- transcript is clearly addressed/directed, or
- user intentionally barged in.

Do not send response.create for ambiguous background speech.

C. Smooth the UI state.

If output_audio_buffer.stopped fires temporarily during a continuing response, do not immediately flip UI to listening unless:
- response.done fired, or
- output_audio_buffer.cleared was client-initiated, or
- a short debounce confirms audio really ended.

This may fix the “glitch in between talking” if it is visual/state flicker.

D. Detect false barge-in during Ora speech.

If assistant_cancelled_for_barge_in appears during the glitch, then Ora is still being interrupted by mic input.
In that case, tighten barge-in confirmation:
- require stronger directed partial transcript outside focus window
- increase barge-in confirm time slightly
- keep echo guard active

4. Compare Focused vs Normal mode.

Normal mode should be faster because the server auto-responds.
Focused mode should be safer.

Test both:
- Normal: speed baseline
- Focused: safety baseline

Do not ship Normal as default unless user accepts the background-speaker risk.

5. QA tests.

Website first:

A. Focused mode, quiet room:
Measure delay after user stops speaking.

B. Focused mode, background speaker:
Ora should stay focused and not respond.

C. Focused mode, intentional interruption:
Ora should stop quickly.

D. Long Ora spoken reply:
Check if audio glitches or only the UI state flickers.

E. Normal mode:
Compare speed and smoothness.

F. Arabic / English / Spanish:
Make sure latency fixes do not break language lock.

Definition of done:
- We know exactly where the delay happens.
- Focused mode remains protected from background speakers.
- Ora replies faster if safe tuning is possible.
- Mid-speech glitch is either fixed or clearly identified as network/model/browser playback.
- No TestFlight build until website Talk to Ora feels stable.
