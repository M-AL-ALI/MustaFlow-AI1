1. React/Vite static projects must run their immutable candidate correctly

`Test Preview - Static Candidate` cannot simply serve raw snapshot source files for a React/Vite project.

A frontend-only React/Vite app still requires Vite/build processing, module resolution and environment injection.

Required correction:

For frontend-only React/Vite projects:
- When starting Test Preview, create the immutable Test Candidate snapshot.
- Run Quick/Test Preview from that candidate snapshot using an isolated WebContainer instance or an immutable build artifact generated from that snapshot.
- Do not read from live `project_files` after candidate creation.
- Inject only explicitly approved `public-client` testing variables needed for the frontend build.
- Never inject server secrets into a browser/WebContainer frontend runtime.
- Mark the candidate stale on later draft changes.
- Approve and publish only the exact candidate that was rendered and tested.

For plain static HTML/CSS/JS projects:
- Serving the immutable snapshot directly is acceptable.

Required tests:
- React/Vite Test Preview mounts files from the candidate snapshot, not live draft files.
- A draft edit after candidate start does not alter the running tested React/Vite candidate.
- Server-scoped testing secrets are not sent into the browser/WebContainer runtime.
- Published React/Vite files come from the approved tested candidate.

2. Production deploy must be true blue/green and switch traffic only after health passes

The current Phase 9 wording is ambiguous and potentially unsafe:

- deploy to prod container
- health check
- traffic switch described as already done for full-stack

Required correction:

For full-stack production deployment:

1. Load files only from `testedSnapshotId.filesSnapshot`.
2. Analyze migrations before any deployment begins.
3. Create a new green production container with Production secrets.
4. Sync the tested snapshot files into the green container.
5. Start the green container.
6. Run allowed production migration policy, if applicable.
7. Health-check the green container directly using its private/new URL.
8. Only after health passes, atomically update public routing fields:
   - `previousPublishedSnapshotId = old publishedSnapshotId`
   - `publishedSnapshotId = testedSnapshotId`
   - `prodContainerId = greenContainerId`
   - `prodContainerUrl = greenContainerUrl`
   - `prodContainerStatus = running`
9. After the switch succeeds, stop or retain the old container for rollback according to policy.
10. If any step before traffic switch fails, destroy the green container and leave all current public routing fields unchanged.

Public slug URLs and custom domains must continue routing to the previous production container/snapshot until step 8 succeeds.

Required tests:
- Green container health checks happen before `prodContainerUrl` changes.
- Failed green deploy leaves existing `prodContainerId`, `prodContainerUrl` and `publishedSnapshotId` unchanged.
- Both public slug and custom domain continue serving the old version during failed deployment.
- Successful deploy switches snapshot and container pointers together.

3. Restrict automatic production migrations more strongly

The current allowlist treats operations such as `ADD CONSTRAINT` as automatically safe. That is not safe enough for live production.

For the first release, use a conservative policy:

Automatically allowed only when clearly validated:
- `CREATE TABLE` for a new table with no destructive statements.
- `ALTER TABLE ... ADD COLUMN` only when the new column is nullable or has a safe default.
- `CREATE INDEX CONCURRENTLY` where supported and correctly executed outside incompatible transactions.

Blocked from automated publish:
- `DROP TABLE`
- `DROP COLUMN`
- `TRUNCATE`
- `DELETE FROM`
- column renames
- type changes
- `SET NOT NULL` without a proven migration strategy
- `ADD CONSTRAINT` requiring validation of existing live rows
- ordinary `CREATE INDEX` on existing production tables unless explicitly handled safely
- any unrecognized SQL

If accurately validating this subset is too large for this milestone:
- block all production schema-changing publishes for now;
- allow users to test database changes in Preview/Test;
- clearly show that production database promotion will be implemented in a later migration-safe phase.

Do not claim production-safe deployment for database-changing apps until this is enforced.

4. Tighten preview-subdomain security details

The preview subdomain design is approved, with these requirements:

- Wildcard DNS and wildcard TLS must exist for `*.preview.{PLATFORM_DOMAIN}`.
- Use an HttpOnly, Secure host-only cookie on the preview hostname; omit the `Domain` attribute unless there is a specific need to widen scope.
- Use CSP `frame-ancestors` for the exact studio origin or approved studio origins.
- Do not rely on `X-Frame-Options: ALLOW-FROM`; it is obsolete and inconsistently supported.
- Validate the preview session row and current project access on each protected preview request.
- Launch tokens must be one-time use and short-lived.
- Revoke preview sessions when secrets/database/runtime security configuration changes.
- Confirm the browser allows the preview cookie flow when embedded in the studio iframe on the real deployed domain.

Required tests:
- Owner session can launch preview inside the studio iframe.
- Revoked project access immediately blocks an existing preview session.
- Preview responses include `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and correct CSP `frame-ancestors`.
- The preview hostname works with wildcard TLS in the deployed environment.
