Orax must not only look like Codex. It must work like a real Codex-style engineering agent.

Current problem:
Orax UI is getting closer, but the actual work loop is still incomplete. The user should not feel like they are clicking workflow controls. They should feel like they gave a coding task to an agent, and the agent is doing the work inline: inspect, plan, edit, run checks, fix failures, summarize, and prepare PR when appropriate.

Goal:
Make Orax functionally Codex-like, not just visually similar.

Do not touch Ora, public-ai chat, AI Builder, credits, or project chat.

Next implementation target:
Build the full Codex-style autonomous task loop for Orax.

Required behavior:

1. User sends a normal coding request
Example:
- “Fix the login error.”
- “Review this repository and explain how it works.”
- “Improve this mobile layout.”
- “Run tests and fix failures.”

Orax should automatically:
- understand the request,
- inspect relevant repository files,
- explain briefly what it is doing,
- execute the next safe step,
- stop only when it needs approval, missing context, or user decision.

The user should not need to manually press separate workflow buttons for every tiny step.

2. Inline agent progress
The thread should show compact Codex-style progress, not dashboard logs.

Good:
- “Inspecting files”
- “Reading package.json”
- “Drafting change”
- “Running typecheck”
- “Fixing test failure”
- “Ready for review”

Bad:
- checkpoint spam
- artifact IDs
- approval IDs
- “Phase 4B”
- “Current task status”
- “Artifacts: 0”
- long internal workflow reports

3. Agentic execution state machine
Add or improve backend runner states so Orax has a real task lifecycle:

- received_task
- selecting_context
- reading_files
- planning
- editing
- running_checks
- fixing_failures
- ready_for_review
- blocked_needs_user
- awaiting_approval
- completed

The backend should decide the next action based on task state, not on UI panels.

4. Real repository context selection
Orax should not always ask the user what files to read.

It should infer relevant files from:
- user prompt,
- repository scan tree,
- package/framework files,
- recent task context,
- attached screenshots/files,
- previous failures,
- common entry points.

For example:
- login issue → auth routes, login page, auth provider, middleware
- mobile layout issue → app screen, component, styles, navigation
- build failure → package.json, tsconfig, vite/expo config, failing logs
- repository explanation → README, package.json, src/app layout, routes, db schema

If file confidence is high, Orax should request approval for a useful set of files automatically.

5. Plan mode behavior
Already started, but needs to be integrated into the normal runner.

In /plan mode:
- inspect context,
- produce a plan,
- stop before edits,
- wait for Start implementation / continue.

In normal mode:
- inspect,
- plan briefly if needed,
- proceed to implementation if safe.

6. Editing/draft patch flow
After file context is approved/read:
- Orax should generate a real draft patch.
- The patch should be based on the inspected files and task goal.
- It should avoid generic “insufficient context” unless truly blocked.
- If context is insufficient, Orax should request the next specific files automatically.

7. Checks and failure recovery
After drafting changes:
- Orax should decide which checks to run based on repo type.
- For web: lint, typecheck, unit tests, build where available.
- For mobile: mobile typecheck, relevant tests, Expo-safe checks.
- For backend: API typecheck/tests.

If checks fail:
- Orax should read the error,
- explain the issue briefly,
- attempt a fix,
- rerun checks,
- repeat within a safe bounded limit.

8. Approval model
Keep approval controls, but make them Codex-like.

Approval should appear only when needed:
- reading private repo files if required by current security model,
- editing files,
- running commands,
- installing packages,
- pushing branch,
- creating PR.

Approval UI should be inline and simple:
- “Allow Orax to read these files?”
- “Allow Orax to run typecheck?”
- “Allow Orax to apply this patch?”
- “Create pull request?”

No visible internal IDs.

9. PR flow
When work is verified:
- summarize changed files,
- summarize checks,
- show residual risks,
- offer “Create pull request”.
After approval:
- create branch,
- commit changes,
- push branch,
- open PR,
- show PR link inline.

10. Website and mobile parity
Every Orax behavior must work on both:
- website Orax
- mobile Orax

Mobile should be able to:
- start task,
- watch progress,
- approve actions,
- send corrections,
- continue implementation,
- review final summary / PR link.

Do not implement a website-only flow.

11. Slash commands should be helpers, not required
Slash commands are useful, but normal language must work.

Examples:
- “Plan this first” should behave like /plan.
- “Continue” should continue.
- “Run checks” should trigger checks.
- “Create PR” should request PR approval.
- “Explain the repo” should run analysis mode, not patch mode.

12. Backend tests
Add or update API tests for:

- natural coding request auto-starts runner
- greeting like “hi” does not auto-run
- /plan stops before patch
- “continue” after plan proceeds to patch
- file selection uses repo scan/prompt heuristics
- insufficient context requests more files instead of generic failure
- draft patch produces artifact after approved read
- checks run after draft patch approval
- failed checks produce retry/fix attempt
- PR request is blocked until explicit approval
- Ora/public-ai routes are untouched

13. Wiring tests
Update Orax wiring test to enforce:

- website and mobile both show same inline runner states
- no dashboard/workflow-control panels return
- no artifact/approval IDs visible in normal thread
- Orax uses /api/orax routes only
- no public-ai/Ora chat wiring
- mobile and web both expose approve/deny/continue inline actions
- plan mode strip exists on both
- final summary and PR link render on both

After implementation:

“Review this repository and explain how it works.”
Expected:
Orax reads important repo files, explains structure, no patch unless asked.

Test B:
Send:
“Fix a small UI issue in Orax.”
Expected:
Orax inspects files, proposes/creates patch, asks for checks, runs checks, summarizes result.

Test C:
Send:
/plan improve the Orax composer
Expected:
Orax creates a plan and stops. After “continue”, it starts implementation.

Test D:
Mobile:
Start same task from mobile, approve actions, continue, and confirm same thread state appears.

Expected final outcome:
Orax should behave like a Codex-style coding agent:
natural request → inspect context → plan → implement → run checks → fix failures → summarize → PR option.

The interface should stay simple, but the backend behavior must become truly agentic.
