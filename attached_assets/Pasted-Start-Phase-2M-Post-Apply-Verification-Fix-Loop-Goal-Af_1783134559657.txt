Start Phase 2M — Post-Apply Verification + Fix Loop

Goal:
After Orax applies a patch on the desktop, it should behave more like Codex:
apply changes → run safe verification checks → report results inline → if checks fail, prepare the next fix proposal.

Do not touch Ora, public-ai chat, AI Builder, credits, or normal Ora project chat.

Build:
1. After `apply_project_patch` completes, queue a new desktop action:
   `verify_project_patch`

2. Desktop verification should run only allowlisted commands:
   - package manager typecheck if detected
   - test command if detected and safe
   - lint command if detected and safe
   - build command only if safe and not destructive

3. Reuse the command safety classifier:
   - no shell:true
   - no exec
   - no arbitrary PowerShell
   - no git push/deploy/delete commands
   - no secret/env exposure

4. Desktop returns structured result:
   - checks[]
   - name
   - command
   - status: passed / failed / skipped
   - stdout preview
   - stderr preview
   - exitCode
   - durationMs

5. Backend writes inline thread messages:
   - `project_patch_verified` when checks pass
   - `project_patch_verification_failed` when checks fail
   - no raw JSON dump
   - no action IDs/artifact IDs in normal thread

6. Website renders verification results inline under the patch flow:
   - green passed checks
   - red failed checks
   - skipped checks muted
   - “Prepare fix” button if verification failed

7. Mobile renders the same verification summary compactly.

8. If verification fails, prepare the next phase hook:
   - queue or expose `draft_project_fix`
   - do not apply automatically
   - keep approval before writes

Tests:
- wiring test for `verify_project_patch`
- desktop relay handles it
- backend queues it after apply success
- website renders `project_patch_verified`
- mobile renders `project_patch_verified`
- no Ora/public-ai route usage
- no shell/exec/process.cwd unsafe usage
