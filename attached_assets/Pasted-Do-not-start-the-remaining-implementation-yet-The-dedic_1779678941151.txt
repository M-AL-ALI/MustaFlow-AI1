4. Production database migration safety is still missing

Deploying an approved container atomically does not make database migrations safe.

A new production migration can alter the database while the old published app is still serving traffic, breaking the old app before the new deployment is healthy.

- Detect whether the approved version includes database schema or migration changes.
- For the first implementation, require production migration changes to be reviewed and explicitly confirmed.
- Block obviously destructive migrations by default, such as dropping tables/columns or destructive resets.
- Require backward-compatible migrations for zero-downtime deployment.
- Run production migration steps with logs and failure reporting before switching traffic.
- If safe support cannot be implemented now, clearly block publishing database-changing versions instead of claiming production-safe promotion.

Required tests:

- A destructive migration blocks production publish by default.
- Migration failure leaves previous public version active.
- A backward-compatible successful migration plus healthy deployment permits traffic switch.
