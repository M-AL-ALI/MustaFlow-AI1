Part 1 — Add live-voice minute budgets by plan

Current desired limits:
1. Free
   - 20 minutes of Talk to Ora live voice
   - resets every 5 hours

2. Core Pack
   - 60 minutes / 1 hour of Talk to Ora live voice
   - resets every 3 hours

3. Deep Wave
   - 120 minutes / 2 hours of Talk to Ora live voice
   - resets every 3 hours

Implementation details:
- Add a new realtime voice usage window keyed by Clerk userId for signed-in users.
- Anonymous users should map to Free-like behavior or stricter anonymous behavior, whichever is already consistent with existing Ora session limits.
- The budget should meter actual session duration, not just number of minted sessions.
- If exact real-time duration cannot be tracked server-side after the ephemeral token is minted, use a safe reservation/refund/heartbeat design:
  - reserve max allowed duration at mint OR
  - track start timestamp and have client report end duration OR
  - heartbeat every N seconds while session is active
- Recommendation: use server-issued session id + client heartbeat/end call:
  - POST /api/public-ai/realtime/session creates a realtime session record with maxDurationSeconds.
  - Client sends heartbeat every 30 seconds while connected.
  - Client sends end event on stop/teardown.
  - Server accumulates used seconds into a rolling window.
  - If client disappears, cap the charge at last heartbeat + grace window, never unlimited.
- Must be robust against abuse:
  - do not trust client-reported arbitrary duration without server-side cap
  - do not allow multiple overlapping sessions to bypass limits
  - enforce per-user concurrent realtime session limit
  - expire stale active sessions automatically

Suggested backend shape:
- Add a table or durable usage ledger for realtime voice minutes:
  - userId or anon/session key
  - tier
  - windowStart
  - windowEnd / resetAt
  - usedSeconds
  - activeSessionId
  - startedAt
  - lastHeartbeatAt
  - reservedSeconds / chargedSeconds
- Add helper:
  getRealtimeVoiceAllowance(tier):
    free -> { limitSeconds: 1200, windowHours: 5 }
    core -> { limitSeconds: 3600, windowHours: 3 }
    wave -> { limitSeconds: 7200, windowHours: 3 }

- Add endpoints:
  POST /api/public-ai/realtime/session
    - before minting, check remaining seconds
    - set maxDurationSeconds to min(plan remaining seconds, technical max cap)
    - if no remaining seconds, return 429 with resetAt and plan limit info
    - return product-safe fields only

  POST /api/public-ai/realtime/heartbeat
    - body: { realtimeSessionId }
    - update lastHeartbeatAt
    - increment/reconcile used seconds safely

  POST /api/public-ai/realtime/end
    - body: { realtimeSessionId }
    - finalize charged seconds
    - clear active session

  GET /api/public-ai/realtime/diagnostics
    - include product-safe plan allowance:
      {
        enabled,
        available,
        tier,
        usedSeconds,
        remainingSeconds,
        limitSeconds,
        resetAt,
        voicePreset,
        voiceLabel
      }
    - do not expose model names or provider ids

Plan UI:

  - do not show model/provider
- Mobile Settings → Talk to Ora Live Voice:

In-call UI:

Part 2 — Improve Talk to Ora performance

Problem:
User reports Talk to Ora sometimes takes longer to reply and sometimes glitches during talking.

Do not blindly tune VAD or lower safety filters until diagnostics show the slow bucket.

Add/verify privacy-safe timing diagnostics:
For every realtime turn, log these deltas:
- speech_started
- speech_stopped
- transcript_completed
- focus_decision_done
- response_create_sent
- response_created
- output_audio_started
- output_audio_stopped
- response_done

Calculate:
- speech_stopped_to_transcript_ms
- transcript_to_focus_decision_ms
- focus_decision_to_response_create_ms
- response_create_to_response_created_ms
- response_created_to_audio_started_ms
- total_speech_stopped_to_audio_started_ms
- audio_output_cycle_count
- interruption_reason
- focus_accept/reject reason
- selected language
- voice preset
- tier

Never log raw audio or full transcript text.
Char counts and reason codes are okay.

Use diagnostics to classify latency:
1. VAD/transcription slow:
   speech_stopped_to_transcript_ms is large
   → consider VAD threshold/silence tuning

2. Focus filter slow:
   transcript_to_focus_decision_ms or focus_decision_to_response_create_ms is large
   → optimize local focus scoring

3. Model slow:
   response_create_to_response_created_ms is large
   → optimize prompt/session config or model choice

4. Playback slow/glitch:
   response_created_to_audio_started_ms large or output_audio cycles/gaps high
   → investigate WebRTC/audio playback handling

Performance goals:
- For normal short questions, Ora should start responding quickly after the user stops speaking.
- Target: first audio should ideally begin within ~1–2 seconds after speech end when network/model conditions are normal.
- Do not sacrifice speaker-focus safety for speed without a clear fallback.

Part 3 — Improve Talk to Ora capability and spoken answer quality

- concise
- clear
- accurate
- not rambling
- helpful
- capable across broad topics
- can teach/explain
- can reason through plans
- can ask a clarifying question when needed
- can say when uncertain
- can use saved memory/profile/context when allowed
- must not expose underlying providers/models

Backend/session instruction improvements:
- Review realtime session instructions in public-ai/realtime.ts.
- Make sure the voice prompt says:
  - You are Ora, created by MustaFlow.
  - Give spoken answers that are clear, concise, and useful.
  - Prefer short paragraphs and natural spoken language.
  - For teaching, explain step-by-step but keep it conversational.
  - If the user asks for deeper detail, expand.
  - If uncertain, say so and give the best supported answer.
  - Do not reveal model/provider names.
  - Do not say you are ChatGPT/OpenAI.
  - Use the selected language or the language the accepted user turn is in.
  - Ignore rejected/background speaker turns.
  - Do not use rejected turns for language, memory, or answer context.
- Make sure existing memory/profile/project/conversation context is included correctly for signed-in users and omitted for temporary mode.

Important:
Do not make Ora “know everything” by hallucinating.
“Strong capability” means better routing, context, clarity, and truthful uncertainty.
Do not instruct it to pretend certainty.
