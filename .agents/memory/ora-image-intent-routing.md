---
name: Ora image-intent routing is pattern-only
description: Why Ora sometimes refuses to generate images and where the single source of truth lives
---

Ora image generation has NO frontend intent override and NO dedicated frontend endpoint — the web chat posts every non-analysis message to the non-streaming `/public-ai/chat`, and the backend router (`routeOraMessage` in orchestrator.ts) is the SOLE decider of image intent via `ORA_IMAGE_PATTERNS` / `isImageGenerationRequest`.

**Symptom:** Ora replies "I can generate it, but I can't produce the actual image in this chat turn." That reply is the CONVERSATIONAL model talking — it means the image fast-path did NOT fire (pattern miss), so the request fell through to the chat model. The system prompt tells the model it CAN generate images and to never refuse, but the model hedges anyway. So a refusal is almost always a routing/pattern-coverage gap, NOT a provider/config problem and NOT the model being "broken."

**Why:** the patterns historically required a recognized verb + an explicit "visual noun", so natural phrasings missed: "draw a dog" (no visual noun), "a logo for my mechanic app" (no verb), "give me a banner" ("give" not a verb in the list). Provider config (`isImageProviderConfigured()`) and the image branch in chat.ts were fine the whole time.

**How to apply:**
- Diagnose refusals by testing `isImageGenerationRequest(phrase)` directly, not by reading provider/env code. If it returns false, broaden patterns; don't touch the provider.
- When broadening, guard against figurative/instructional false positives: idiom exclusion list after drawing verbs (conclusion/point/concept/idea/line/...), a `(?<!how (to|do i|...) )` lookbehind for tutorials ("how to paint a room"), and anchor any verb-less "a <noun> for/of ..." pattern to `^` so mid-sentence statements ("I used a logo for my app") don't match.
- Router fast-path ORDER matters: file_generation + file-continuation run BEFORE image, image runs BEFORE search. Keep image asks from being eaten by file-continuation ("generate it") or search.
- `image_editing` tool is status `"planned"` in the registry — chat-text "modify this image" does NOT route through the router; editing happens via the inline Edit button → `/images/:id/edit` (shared with Image Studio, which DOES charge credits). Image analysis (`image_analysis`) is live and fires on uploads.

**Auth-state must be injected into the Ora system prompt (false sign-in hedge):** Ora's system prompt has a "not signed in → tell them to sign up" branch for image/search. `buildSystemPrompt` (chat.ts) historically varied ONLY by language and NEVER told the model the caller's auth state, so the model GUESSED and could apply the sign-in branch to a signed-in user ("image generation here is available once you're signed in"). Fix: pass `isSignedIn` (`!!authed`) into `buildSystemPrompt` and emit an authoritative "## Current session" block. Lesson: any prompt branch conditioned on a runtime fact the model can't observe (auth, plan, quota) must be stated explicitly in the prompt, or the model invents it.

**Image-offer CONTINUATION ("go ahead and do it") needs its own router step:** Only file-continuation existed; a short affirmation after Ora OFFERED an image fell through to conversational (which only claims it / re-hedges). Added step "2b" in routeOraMessage (after image fast-path, before search): `detectImageContinuation` resolves a prompt from prior context. The image branch generates with `decision.imagePrompt ?? message` — generateImage takes a single prompt string and NO convo history, so a continuation MUST resolve the real prompt or it'd generate the literal "go ahead" text.

**The continuation gate is a TOKEN-SET allowlist, not affirmation-lead regex.** Earlier an "affirmation-lead + benign-trailer" regex was used, but it (a) misclassified generation-verb replies like "go ahead and CREATE it" / "yes create it" as benign-trailer rejects → still hedged, and (b) was brittle. Replaced with: lowercase, split on whitespace, strip EDGE punctuation per word only (so qualifier tokens like `16:9` survive instead of being scrubbed by a global non-alpha strip — that bug made "make it 16:9" pass as pure continuation), then require EVERY word ∈ `IMAGE_CONTINUATION_TOKENS` (affirmations + gen verbs create/make/generate/build/produce/render/draw/design/sketch/paint/do + refs it/that/the/image/etc + fillers) AND ≥1 word ∈ `IMAGE_CONTINUATION_INTENT_TOKENS` (an affirmation or gen verb). Modifier replies ("make it blue"/"with neon colors"/"make it 16:9") still carry a NEW qualifier word not in the set → fall through (a context-derived prompt would silently discard it → wrong image).

**Questions must be guarded explicitly** — "do you create images", "can you make it" share tokens with continuations but ASK, they don't affirm. Reject if the message contains `?` OR matches `^(do|does|can|could|will|would|should|are|is|have|has)\s+you\b`. (NOTE: "do you create images" is ALSO caught earlier by the base `ORA_IMAGE_PATTERNS` fast-path — `create`+`images` — which is a separate pre-existing path; the continuation gate only governs phrasings that reach step 2b.)

**Prompt resolution must use a TIGHT locality window.** Resolve the prompt by inspecting ONLY the nearest preceding user turn before the offer: if it's an image request use it, else fall back to the offer's descriptive clause (`extractImageOfferDescription`). Walking ALL the way back (the original loop) lets a STALE unrelated earlier image request ("make a logo for my bakery") override the current offer's subject ("a coffee cup") → wrong image generated.
- Routing tests that hit the conversational fallthrough call the live LLM classifier (~4s each) and time out the 5s default when looped. Pass a stub `classifier` in the `routeOraMessage` input (`input.classifier ?? await classifyIntent()`) to skip the network call and keep tests fast/deterministic.

**The "you are not signed in" + image-refusal-for-a-signed-in-user bug was a FRONTEND raw-fetch auth gap, not prompt/routing.** Ora web chat's `apiPost`/`apiGet`/`apiDelete` helpers in `use-ora-chat.ts` used raw cookie-only `fetch` (no bearer). The dev-mode Clerk JWT cookie expires ~60s inside the preview iframe, so `getAuth(req)` on `/public-ai/chat` saw the caller as anonymous → `authed=null` → `checkToolAccess` HARD-gated images with `image_signin_required` (the "Sign up at mustaflow.app" CTA) AND `buildSystemPrompt` got `isSignedIn=false`. Tell-tale signal in server logs: `Ora chat completion ... planTier: "anonymous"` for a user who IS signed in. Fix: route those helpers through `authFetch` (`lib/api-fetch.ts`), which attaches a fresh bearer token and keeps `credentials:"include"`. Lesson (reinforces customfetch-token-getter-resilience + clerk-jwt-expiry-401): EVERY raw `/api` call that bypasses Orval must use `authFetch`; cookie-only requests intermittently authenticate as anonymous in the preview iframe. The bare "mustaflow.app" CTA link is NOT auto-linked by OraRichText (only `http(s)://` is) — the clickable, preview-unreachable link came from the conversational model emitting `https://mustaflow.app`; it only resolves once the app is actually deployed to that domain, and signed-in users no longer see the CTA at all after the auth fix.
