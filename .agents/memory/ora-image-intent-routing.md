---
name: Ora image-intent routing is pattern-only
description: Why Ora sometimes refuses to generate images and where the single source of truth lives
---

Ora image generation has NO frontend intent override and NO dedicated frontend endpoint — the web chat posts every non-analysis message to the non-streaming `/public-ai/chat`, and the backend router (`routeOraMessage` in orchestrator.ts) is the SOLE decider of image intent via `ORA_IMAGE_PATTERNS` / `isImageGenerationRequest`.

**Symptom:** Ora replies "I can generate it, but I can't produce the actual image in this chat turn." That reply is the CONVERSATIONAL model talking — it means the image fast-path did NOT fire (pattern miss), so the request fell through to the chat model. The system prompt tells the model it CAN generate images and to never refuse, but the model hedges anyway. So a refusal is almost always a routing/pattern-coverage gap, NOT a provider/config problem and NOT the model being "broken."

**Why:** the patterns historically required a recognized verb + an explicit "visual noun", so natural phrasings missed: "draw a dog" (no visual noun), "a logo for my mechanic app" (no verb), "give me a banner" ("give" not a verb in the list). Provider config (`isImageProviderConfigured()`) and the image branch in chat.ts were fine the whole time.

**Pattern expansion (important):** After a second audit, the noun list still missed many very common phrasings: "generate a scene", "create concept art", "make a background", "visualize a robot", "generate a meme", "create a cartoon", "make a sticker", "generate a render", "I want a landscape", "create digital art". These were added to Patterns 1, 4, 5, 7. A standalone `visualize` pattern was added (with data-context guard so "visualize the data" stays blocked). An `ORA_IMAGE_GENERATION_BLOCKLIST` was added to prevent false positives: "character profile/backstory" → writing (not image), "background on/about X" → informational (not image background), "describe a scene" → narrative analysis. Coverage went from ~22% to 100% on a representative test suite with 0 false positives.

**How to apply:**
- Diagnose refusals by testing `isImageGenerationRequest(phrase)` directly via node --input-type=module. If it returns false, broaden patterns; don't touch the provider.
- When broadening, guard against figurative/instructional false positives: idiom exclusion list after drawing verbs (conclusion/point/concept/idea/line/...), a `(?<!how (to|do i|...) )` lookbehind for tutorials ("how to paint a room"), and anchor any verb-less "a <noun> for/of ..." pattern to `^` so mid-sentence statements ("I used a logo for my app") don't match.
- Add new false-positive blocklist entries to `ORA_IMAGE_GENERATION_BLOCKLIST` rather than complicating existing patterns.
- Router fast-path ORDER matters: file_generation + file-continuation run BEFORE image, image runs BEFORE search. Keep image asks from being eaten by file-continuation ("generate it") or search.
- `image_editing` tool is status `"planned"` in the registry — chat-text "modify this image" does NOT route through the router; editing happens via the inline Edit button → `/images/:id/edit` (shared with Image Studio, which DOES charge credits). Image analysis (`image_analysis`) is live and fires on uploads.

**Clarification loop — `detectImagePostClarification` (step 2d):** When patterns miss, the LLM in conversational mode asks clarifying questions about the image. The user's description reply ALSO misses patterns → endless loop. Fixed by adding step 2d in `routeOraMessage` (after 2c continuation, before search): `detectImagePostClarification` fires when (a) the last assistant turn references image nouns AND contains question-seeking language (what style, could you describe, tell me more, etc.) AND (b) the current user message is a non-question description 8–400 chars. It builds a combined prompt from the nearest prior matched image request + the new details. Prompt resolution uses last-8-messages window to avoid stale context.

**Auth-state must be injected into the Ora system prompt (false sign-in hedge):** Ora's system prompt has a "not signed in → tell them to sign up" branch for image/search. `buildSystemPrompt` historically varied ONLY by language and NEVER told the model the caller's auth state, so the model GUESSED and could apply the sign-in branch to a signed-in user ("image generation here is available once you're signed in"). Fix: pass `isSignedIn` (`!!authed`) into `buildSystemPrompt` and emit an authoritative "## Current session" block. Lesson: any prompt branch conditioned on a runtime fact the model can't observe (auth, plan, quota) must be stated explicitly in the prompt, or the model invents it.

**Image-offer CONTINUATION ("go ahead and do it") needs its own router step:** Only file-continuation existed; a short affirmation after Ora OFFERED an image fell through to conversational (which only claims it / re-hedges). Added step "2c" in routeOraMessage (after image fast-path, before search): `detectImageContinuation` resolves a prompt from prior context. The image branch generates with `decision.imagePrompt ?? message` — generateImage takes a single prompt string and NO convo history, so a continuation MUST resolve the real prompt or it'd generate the literal "go ahead" text.

**The continuation gate is a TOKEN-SET allowlist, not affirmation-lead regex.** Earlier an "affirmation-lead + benign-trailer" regex was used, but it misclassified gen-verb replies like "go ahead and CREATE it" and was brittle. Replaced with: lowercase, split on whitespace, strip EDGE punctuation per word only (so qualifier tokens like `16:9` survive), then require EVERY word ∈ `IMAGE_CONTINUATION_TOKENS` AND ≥1 word ∈ `IMAGE_CONTINUATION_INTENT_TOKENS`. Modifier replies ("make it blue"/"make it 16:9") still carry a NEW qualifier word → fall through to `detectImagePostClarification` which builds a combined prompt.

**Questions must be guarded explicitly** — "do you create images", "can you make it" share tokens with continuations but ASK, they don't affirm. Reject if the message contains `?` OR matches `^(do|does|can|could|will|would|should|are|is|have|has)\s+you\b`.

**Prompt resolution must use a TIGHT locality window.** Resolve the prompt by inspecting ONLY the nearest preceding user turn before the offer: if it's an image request use it, else fall back to the offer's descriptive clause (`extractImageOfferDescription`). Walking ALL the way back lets a STALE unrelated earlier image request override the current offer's subject → wrong image generated.

**System prompt rule (clarification prevention):** ORA_SYSTEM_PROMPT now explicitly says to NEVER ask clarifying questions before generating an image — generate immediately with whatever description was given, then offer to refine. This backstops the pattern gaps and prevents the LLM from starting clarification loops even when the conversational fallthrough is reached.

**The "you are not signed in" + image-refusal-for-a-signed-in-user bug was a FRONTEND raw-fetch auth gap, not prompt/routing.** Ora web chat's `apiPost`/`apiGet`/`apiDelete` helpers in `use-ora-chat.ts` used raw cookie-only `fetch` (no bearer). The dev-mode Clerk JWT cookie expires ~60s inside the preview iframe, so `getAuth(req)` on `/public-ai/chat` saw the caller as anonymous → `authed=null` → `checkToolAccess` HARD-gated images with `image_signin_required`. Fix: route those helpers through `authFetch`. Lesson: EVERY raw `/api` call that bypasses Orval must use `authFetch`; cookie-only requests intermittently authenticate as anonymous in the preview iframe.
