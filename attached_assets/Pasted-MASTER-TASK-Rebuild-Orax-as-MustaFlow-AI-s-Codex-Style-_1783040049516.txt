MASTER TASK — Rebuild Orax as MustaFlow AI’s Codex-Style Desktop Coding Agent + Web/Mobile Remote Control

Important:
We are rebuilding Orax correctly.

Orax must not be only a website/mobile chatbot. Orax must become MustaFlow AI’s Codex-style coding and workflow agent with a real local desktop host, PowerShell/terminal execution, file access, Git/GitHub workflow, web/mobile remote control, billing/usage tracking, and secure approval controls.

Do not touch Ora.

Ora must remain the main AI assistant experience. Orax is separate:
- Ora = main AI assistant
- Orax = coding/workflow agent
- Orax Desktop = installed local coding agent/app
- Orax Web = product/download page + remote control/management surface
- Orax Mobile = remote control inside Ora mobile
- MustaFlow Cloud = auth, billing, usage, host pairing, thread sync, relay, notifications, audit logs

Orax can reuse shared MustaFlow infrastructure where safe:
- auth/account
- billing/usage
- support/help
- design tokens
- backend shared utilities

But Orax must not modify or couple itself to:
- Ora chat runtime
- public-ai chat routes
- AI Builder
- project chat
- unrelated credits UI logic
- unrelated billing internals
- unrelated mobile screens

Do not copy OpenAI branding or proprietary implementation. The goal is functional equivalence under MustaFlow AI architecture and branding.

Official Orax Logo:
Use the provided Orax logo as the official identity. It is the small terminal-style square icon with a `>_` prompt. Make it professional, clean, and consistent across:
- Orax website card
- Orax download page
- Orax Desktop app icon
- Orax Desktop sidebar
- Orax Mobile entry point
- loading states
- empty states
- connected host state

High-Level Product Vision:
Orax should behave like a real agentic AI software engineer.

User gives a natural request:
- “Fix the login bug.”
- “Review this repository.”
- “Improve this layout.”
- “Run tests and fix failures.”
- “Create a pull request.”

Orax should:
- understand the task
- inspect project files
- plan
- edit files
- run PowerShell/terminal commands
- run tests/typechecks/builds
- debug failures
- retry fixes
- summarize work
- create GitHub branches/PRs after approval
- let the user continue from desktop, web, or mobile

Everything should happen inline in the chat thread, not through dashboard-style workflow panels.

Core Architecture:
Orax Desktop is the worker.
Orax Web and Orax Mobile are remote-control surfaces.
MustaFlow Cloud handles identity, relay, sync, billing, pairing, notifications, and audit logs.

PHASE 3 — Computer Access, Permissions, and Sandbox Modes

Orax Desktop must support configurable local computer access.

The goal is to let Orax use PowerShell, terminal commands, Git, Node.js, package managers, JSON/config files, build tools, and local project files like a real coding agent, while giving the user clear control over risk.

Default mode:
Use “Ask for Risky Actions” as the default.

Access modes:

1. Read Only
- Can inspect approved project files.
- Can explain code.
- Cannot edit files.
- Cannot run shell commands.
- Cannot push to GitHub.

2. Ask Before Everything
- Requires approval before file reads, edits, commands, installs, Git actions, and PR creation.
- Safest interactive mode.

3. Ask for Risky Actions
- Can automatically perform low-risk actions inside approved project folders.
- Must ask before risky actions.
- Low-risk examples:
  - read normal source files
  - list files
  - inspect package.json
  - git status
  - git diff
  - run configured safe checks like typecheck/test if user enabled them
- Risky examples:
  - edit files
  - delete files
  - install packages
  - run unknown commands
  - change env/config/secrets
  - push to GitHub
  - create PR
  - deploy

4. Trusted Project Mode
- For selected projects only.
- Can read/edit project files and run configured project commands.
- Still asks for destructive/system-level actions.
- Still asks before reading secrets or pushing/deploying.

5. Full Access / Advanced Mode
- User explicitly allows broader local command and file access.
- Must show strong warning before enabling.
- Not default.
- Should still block or double-confirm destructive/system commands.
- Should be reversible at any time.

6. Custom Mode
User can define:
- allowed folders
- blocked folders
- allowed commands
- blocked commands
- commands that always require approval
- whether file edits are automatic or approval-based
- whether package installs require approval
- whether Git commits/pushes require approval
- whether `.env` and secret files can be read
- whether network commands are allowed
- whether browser/computer-use is allowed

Permission categories:
- Filesystem
- Shell/PowerShell
- Git
- Package managers
- Network
- Browser/computer-use
- Secrets
- Deployment

Security requirements:
- Orax can only access approved project folders by default.
- Commands run inside project working directory unless explicitly approved.
- All commands have timeout.
- All command output is scanned/redacted for secrets.
- Destructive commands require approval or are blocked.
- Reading `.env`, private keys, tokens, or credentials requires explicit approval.
- Full access mode requires clear warning and confirmation.
- Users can change permission mode anytime from Settings.
- Users can set permissions globally or per project.
- All approvals/actions are logged for audit.

Desktop UI:
Settings should include “Computer Access” or “Permissions” page with:
- current mode
- folder access list
- command allowlist
- command blocklist
- Git permissions
- package install permissions
- secrets policy
- browser/computer-use toggle
- reset to safe defaults

Inline approval examples:
- “Allow Orax to read these files?”
- “Allow Orax to edit these files?”
- “Allow Orax to run `pnpm typecheck` in this project?”
- “Allow Orax to install `lucide-react`?”
- “Allow Orax to push branch `orax/fix-login` to GitHub?”
- “Allow Orax to read `.env.local`? This may contain secrets.”

Expected behavior:
Orax should feel powerful like Codex, but controlled. Users can choose strict approvals, risky-action approvals, trusted project behavior, or advanced full access.

PHASE 4 — Account Identity, Billing, Usage, and Device Sync

This is critical.

Users may buy a new desktop/laptop and install Orax again. When they sign in with the same MustaFlow account, they should recover their Orax cloud state.

Account identity:
- Every Orax session must link to MustaFlow userId.
- Usage and billing track by userId and workspace/accountId.
- Device/host ID identifies which computer performed the work.

Device identity:
Each Orax Desktop installation creates/registers:
- hostId/deviceId
- userId
- deviceName
- platform
- appVersion
- capabilities
- lastSeenAt
- online/offline status

Device ID is not a password. It is an internal identifier for the specific computer/app install.

Cloud sync:
When user installs Orax on a new computer and signs in:
- user profile loads
- billing/usage loads
- connected devices load
- previous Orax threads load
- project records load
- GitHub/app integrations load if cloud-managed
- local-only project paths may need reconnecting because file paths are machine-specific

Important:
Cloud can restore threads, metadata, settings, account, billing, device list, and integration records.
Cloud cannot magically restore local files that only existed on the old computer unless they were committed/pushed/synced through GitHub or another remote.

If a previous project path is unavailable on the new computer:
Show:
“This project was connected on another device. Clone from GitHub or reconnect the local folder to continue.”

Billing/usage events:
Every billable Orax action should report:
- userId
- workspaceId/accountId
- hostId/deviceId
- projectId
- threadId
- action type
- model used
- tokens/compute units
- timestamp
- status

Trackable Orax usage:
- model calls
- screenshot/image analysis
- file/repository analysis
- long-running agent task
- cloud relay usage if applicable
- premium integrations if applicable

Local-only audit events:
- command started/completed
- file edit requested/applied
- approval accepted/denied
- git status checked

Credits:
- Check credits before billable model work.
- If insufficient:
  “You need more credits to continue this Orax task.”
- Link to Billing & Usage.
- Keep Orax usage separate from Ora chat history, but account billing balance can be shared.

PHASE 6 — Orax Mobile Pairing and Remote Control

Orax Mobile is a remote-control surface for Orax Desktop.

First-time mobile flow:
1. User opens Orax Mobile.
2. If no host is paired, show “Connect Orax Desktop”.
3. Explain that Orax Desktop must be installed and open on the user’s computer.
4. User taps “Scan QR Code” or “Enter Pairing Code”.
5. User scans the QR code shown in Orax Desktop.
6. Mobile pairs with that desktop host.
7. Mobile shows the host as connected.

Pairing options:
- QR code
- manual pairing code
- same MustaFlow account verification
- optional device approval from desktop

Connected host state:
Mobile should show:
- host name
- platform
- online/offline status
- last seen time
- active project
- active thread
- available capabilities

Online requirement:
For mobile to control local coding tasks, the desktop host must be:
- powered on
- awake
- online
- running Orax Desktop
- signed in
- paired
- not revoked

If desktop is offline:
- mobile must show offline state
- mobile can show previous history/results
- mobile cannot run local commands
- mobile cannot edit local files
- mobile cannot continue local execution
- mobile can notify user to reopen Orax Desktop

Offline message:
“Keep Orax Desktop open and your computer awake to continue local coding tasks from mobile.”

Remote control actions from mobile:
When host is online, mobile can:
- start a new Orax thread
- continue an existing thread
- send follow-up instructions
- approve file reads
- approve file edits
- approve command execution
- approve Git/GitHub actions
- attach screenshots
- review progress
- receive final summaries

Security:
- pairing must be account-bound
- user can revoke paired devices
- QR code must expire
- pairing code must expire
- mobile cannot access a host from another account
- host can require desktop-side approval for first pairing

Multiple devices:
- A user can pair multiple phones/tablets to one desktop.
- A user can pair one phone to multiple desktops.
- Mobile should allow switching hosts.

Host offline handling:
If host goes offline during a task:
- show “Host disconnected”
- preserve thread state
- resume automatically when host reconnects if safe
- ask user before continuing risky actions after reconnect

Expected behavior:
Orax Mobile behaves like a remote controller for the desktop agent. It does not pretend to execute local coding work by itself.
