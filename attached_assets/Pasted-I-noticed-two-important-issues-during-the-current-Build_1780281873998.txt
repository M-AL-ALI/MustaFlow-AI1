1. File-write verification issue
    If write_file reports success, the system must immediately verify the file exists in the same source of truth used by the preview and quality gate.

Verify:

* Was the file written to the container?
* Was the file written to project_files?
* Was the file written to the correct project ID?
* Was the path sanitized or changed?
* Was the file written to /app but not persisted to DB?
* Was the file written to DB but not synced to /app?
* Was the preview reading an older version/snapshot?

If write_file says success but the file cannot be read back, the agent should not keep going blindly.

Required behavior:

* Read the file back immediately after write.
* If missing, retry once.
* If still missing, stop the task with a clear blocker:
    “File write verification failed.”
* Show the exact path and source that failed.
* Do not continue looping.

2. Agent stuck-loop detection
    The agent should not repeat the same failing action over and over.

Add stuck-loop detection for:

* same file path
* same failed tool
* same TypeScript error
* same preview error
* same command failure
* same “file did not appear” message
* same failed repair attempt

Suggested rule:
If the same failure happens 2 or 3 times, the agent must change strategy.

Possible strategy changes:

* Re-read the file tree.
* Re-sync project_files to container.
* Rebuild the file from scratch.
* Revert to last checkpoint and apply a smaller patch.
* Switch from patch editing to full-file replacement.
* Ask the user for approval or clarification.
* Stop and report “blocked” instead of looping.

3. Repair loop must try different directions
    The TypeScript repair loop should not just send the same error back to the agent and hope it fixes it.

If repair attempt 1 fails:

* summarize what changed
* compare old error vs new error
* identify whether the error improved, changed, or stayed the same

If the same error remains:

* try a different repair strategy
* do not repeat the same patch style
* consider reverting the bad file
* inspect imports/exports/types
* inspect related files, not only the file named in the error

If repair attempts are exhausted:

* mark the task as completed_with_errors or failed
* show the user the real blocker
* do not show clean success
