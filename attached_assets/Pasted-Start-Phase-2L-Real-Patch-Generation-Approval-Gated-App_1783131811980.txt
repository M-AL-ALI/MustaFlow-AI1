Start Phase 2L — Real Patch Generation + Approval-Gated Apply

Goal:
Move Orax from “draft patch preview” to the first real Codex-like edit loop:
inspect files → generate real proposed code changes → show inline diff → user approves → desktop applies changes safely.

Important:
Do not touch Ora, public-ai chat, AI Builder, credits, or normal Ora project chat.
Only work inside Orax backend, Orax desktop, Orax website, Orax mobile, and Orax wiring tests.

Current state:
Phase 2K is verified. Orax can draft a patch proposal, but it is still a deterministic/skeleton proposal. The next gap is making Orax produce real code changes and apply them only after approval.

Also cleanup:
Remove the accidentally committed prompt artifact unless it is intentionally needed:
`attached_assets/Pasted-Start-Phase-2K-Orax-Draft-Patch-Proposal-Loop-Goal-Move_1783129303417.txt`

Done Looks Like:
- Orax can generate a real patch proposal from safely-read project files.
- The proposal is shown inline in the Orax thread on website and mobile.
- No file writes happen until the user approves.
- After approval, Orax Desktop applies the patch locally.
- Desktop validates every path before writing.
- Desktop creates a checkpoint/backup before modifying files.
- Backend writes a clear inline result message: files changed, what changed, and next step.
- No raw JSON dumps, action IDs, artifact IDs, or dashboard-like logs in the normal thread.
- Ora remains untouched.

Implementation Plan:

1. Upgrade patch proposal shape
Update Orax patch payload to support real changes:

- `relativePath`
- `operation`: update/create
- `originalHash`
- `oldContentPreview`
- `newContent`
- `unifiedDiffPreview`
- `reason`

Prefer structured file replacement over shell-based patching. Do not use `git apply`, `exec`, `spawn`, or `shell:true`.

2. Add safe file-content handoff
Phase 2J reads safe file previews locally. For real patch generation, backend/model needs enough context.

Add a capped, safe `filePreviews` payload from desktop to backend:
- relative paths only
- contentPreview only
- max total content size enforced
- no blocked files
- no `.env`, keys, certs, tokens, secrets
- no absolute paths
- no symlink escapes

3. Generate real patch proposal
Use existing MustaFlow/Orax AI provider pattern if available.

Backend should generate structured proposed changes using:
- user message
- selected file previews
- project inspection summary
- suggested plan

The AI output must be parsed/validated into a strict schema.
If schema validation fails, return an inline “I could not safely draft this patch” message.

4. Store proposal inline
When proposal is generated, backend writes:
`eventType: "project_patch_drafted"`

Website/mobile should render:
- summary
- changed file chips
- diff preview
- risks
- verification plan
- approval button: “Apply patch”

No raw JSON.

5. Add approval-gated apply action
Add backend endpoint / action flow:

- user clicks Approve / Apply patch
- backend creates `apply_project_patch` desktop action
- desktop receives action through relay
- desktop validates:
  - project binding matches `.orax/project.json`
  - all paths are relative
  - no `..`
  - no absolute paths
  - no blocked dirs/files
  - realpath stays inside project root
  - originalHash matches current file content for updates
- desktop writes checkpoint before applying
- desktop writes files using fs APIs only
- desktop returns result:
  - changedFiles[]
  - checkpointPath
  - warnings[]
  - durationMs

6. Desktop checkpoint
Before applying any patch, create a local checkpoint under:

`.orax/checkpoints/<threadId>/<timestamp>/`

Store:
- original file copies for updated files
- metadata.json with projectId, threadId, executionSourceId, changedFiles, createdAt

Do not include secrets or blocked files.

- `project_patch_drafted`
- `project_patch_applied`

The patch card should feel Codex-like:
- simple
