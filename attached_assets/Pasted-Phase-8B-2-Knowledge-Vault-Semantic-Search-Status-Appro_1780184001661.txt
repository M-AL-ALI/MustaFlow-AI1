Phase 8B-2 — Knowledge Vault Semantic Search

Status: Approved to Begin

Goal

Build semantic search for the Knowledge Vault using the embedding infrastructure completed in Phase 8B-1.

This phase should allow authenticated users to search their saved Knowledge Vault entries by meaning, not only by exact keywords.

This phase is search only.

Do not implement RAG yet.

Do not inject vault knowledge into Ora prompts yet.

Do not create AI memory yet.

Do not implement automatic recommendations yet.

Do not allow Ora or Builder to automatically use Knowledge Vault entries yet.

⸻

Current Stable Baseline

Already accepted:

* Phase 8A — Knowledge Vault Foundation
* Phase 8A.1 — Tags TEXT[], FTS GIN indexes, OpenAPI/client/frontend aligned
* Phase 8B-1 — Embedding Infrastructure
* Ora mobile layout bug fix accepted
* Current rollback checkpoint remains stable

Phase 8B-2 must build on top of the existing vault_embeddings table and embedding service.

⸻

Scope of Phase 8B-2

In Scope

Implement:

1. Semantic search endpoint
2. Hybrid search endpoint if practical
3. Query embedding generation
4. Vector similarity search using pgvector
5. Result ranking
6. Metadata filters
7. Frontend semantic search UI
8. Search result cards
9. Result explanation fields
10. Full validation report

⸻

Out of Scope

Do NOT implement:

* RAG
* AI answer generation from vault
* prompt injection
* automatic report improvement
* automatic recommendations
* automatic learning
* auto-saving
* background autonomous knowledge processing
* cross-project intelligence
* Web Search
* Image Generation
* Advanced Charts
* unrelated roadmap work

Semantic search should only return matching vault entries/chunks.

⸻

Backend Requirements

Create authenticated route:

POST /api/vault/search/semantic

Suggested request body:

{
  query: string;
  limit?: number;
  category?: string;
  department?: string;
  tags?: string[];
  status?: string;
  includeArchived?: boolean;
}

Suggested response:

{
  query: string;
  results: Array<{
    entryId: number;
    title: string;
    category: string;
    department?: string;
    summary: string;
    tags: string[];
    status: string;
    version: number;
    chunkIndex: number;
    chunkPreview: string;
    similarityScore: number;
    keywordScore?: number;
    hybridScore?: number;
    updatedAt: string;
  }>;
}

⸻

Search Logic

Use:

* text-embedding-3-small
* same 1536 dimensions as Phase 8B-1
* pgvector similarity search

Generate embedding for the user query.

Search only the authenticated user’s embeddings.

Never search another user’s embeddings.

Never expose raw vectors.

Never return full chunk text if not needed. Use a safe preview.

⸻

Similarity Scoring

Use pgvector cosine distance or equivalent.

Example:

ORDER BY embedding <=> query_embedding

or the correct operator based on the selected pgvector distance type.

Return normalized score if possible:

similarityScore: number; // 0–100 or 0–1, but document which one

⸻

Hybrid Search

If practical in this phase, combine:

* semantic score from vector search
* keyword score from existing full-text search
* metadata filters from category / department / tags / status

If hybrid search adds too much risk, implement semantic-only first and leave hybrid ranking for 8B-2B.

Do not delay semantic search because of hybrid complexity.

⸻

Filters

Semantic search must support filters:

* category
* department
* tags
* status
* archived / non-archived

Filters must be applied with ownership checks.

⸻

Security Requirements

All routes must:

* require authentication
* enforce user ownership
* only search the authenticated user’s entries
* not expose raw vectors
* not expose another user’s chunks
* not log query text if avoidable
* not log chunk text
* not log raw vault content

Safe logging only:

* user hash if needed
* result count
* latency
* model name
* error category

⸻

Privacy Requirements

Do not send vault entries to the model during search.

Only the user search query is embedded.

The stored entry chunks are already embedded from Phase 8B-1.

The search process should compare vectors in the database.

Do not call the AI model to summarize results.

Do not generate an answer from results.

Return search matches only.

⸻

Frontend Requirements

Update the Knowledge Vault page with:

1. Search mode toggle:
    * Keyword Search
    * Semantic Search
2. Semantic search input:
    * placeholder: “Search by meaning, example: sealing failures, downtime root causes, WBI improvement actions”
3. Result cards should show:
    * title
    * category
    * department
    * tags
    * summary
    * best matching chunk preview
    * similarity score
    * updated date
4. Clicking a result opens the existing entry viewer.
5. If no embeddings exist:
    * show message: “This entry has not been indexed yet. Rebuild embeddings to include it in semantic search.”
6. If no results:
    * show helpful empty state
7. Do not show raw vectors.

⸻

Reindex Dependency

If user searches before indexing entries, show a clear message:

“Semantic search requires indexed Knowledge Vault entries. Reindex your vault first.”

Optionally include button:

“Reindex My Vault”

This should call the existing Phase 8B-1 reindex endpoint.

⸻

Rate Limits

Semantic search should be rate-limited because each query creates a new embedding.

Suggested:

* 30 semantic searches per hour per user

If using another limit, explain why.

This rate limit must not affect:

* regular vault CRUD
* keyword search
* Ora public chat
* Builder
* Developer Mode
* Plan Mode

Acceptance Criteria

Phase 8B-2 is complete only when:

* authenticated user can run semantic vault search
* search uses query embeddings
* search compares against vault_embeddings
* results are scoped to the authenticated user
* filters work
* result ranking works
* raw vectors are never returned
* no RAG is implemented
* no AI memory is implemented
* no prompt injection is implemented
* all quality gates pass

This phase should make the Knowledge Vault searchable by meaning, but it must not allow Ora or Builder to automatically use the vault yet.
