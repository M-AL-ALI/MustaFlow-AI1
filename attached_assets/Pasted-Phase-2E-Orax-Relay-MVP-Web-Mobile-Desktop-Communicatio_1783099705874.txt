Phase 2E — Orax Relay MVP: Web/Mobile ↔ Desktop Communication Bridge

Context:
Phase 2D is complete and verified.

Current working state:
- Orax Desktop app exists.
- Desktop can register itself as a host.
- Desktop heartbeat works.
- Website/mobile can list Orax Desktop hosts.
- Website/mobile can show online/offline state.
- Website/mobile can pair/manage desktop devices.
- Website/mobile host status and permissionMode now match backend contract.
- Orax Desktop build passes.
- Orax wiring test passes.

Important:
Orax still does NOT behave like Codex yet because there is no real live relay between website/mobile and desktop. Website/mobile can see the desktop, but cannot yet send work to it and receive live execution progress back.

Goal of Phase 2E:
Build the first real Orax relay loop.

The user should be able to:
1. Open Orax on website or mobile.
2. Select an online Orax Desktop host.
3. Send a safe test action, such as “ping desktop” or “get desktop status”.
4. Backend relays that action to the desktop.
5. Desktop receives it.
6. Desktop responds with progress/events.
7. Website/mobile shows those events inline in the Orax thread.

This phase is NOT full command execution yet.
Do not run PowerShell, terminal commands, git commands, file edits, PR creation, or package installs in Phase 2E.
This phase proves the communication bridge only.

Do not touch:
- Ora
- public-ai
- AI Builder
- credits
- project chat
- existing Ora routes

Core architecture:
Desktop connects outward to MustaFlow backend.
Website/mobile talks to MustaFlow backend.
Backend relays messages between website/mobile and desktop.

Do not require inbound ports on the user’s desktop.
Do not require LAN-only access.
The desktop should initiate the connection, similar to a secure cloud relay.

Part A — Backend relay route

Add a new Orax relay route.

Suggested endpoint:
GET /api/orax/relay

This should support WebSocket upgrade if the current API server supports WebSocket infrastructure.

If WebSocket support is too large for this pass, use a safe fallback:
- POST action queue endpoint
- GET long-poll/poll endpoint for desktop
- POST event endpoint for desktop responses

Preferred:
WebSocket relay.

Fallback acceptable for MVP:
HTTP polling relay, but structure it so it can be replaced by WebSocket later.

Required backend behavior:
- Authenticated desktop connects as a specific host.
- Backend verifies the host belongs to the signed-in user.
- Backend rejects revoked hosts.
- Backend marks host online while relay is connected.
- Backend marks host offline/stale when disconnected or heartbeat expires.
- Backend can send queued actions to that host.
- Backend receives events from that host.
- Backend stores relay events in the relevant Orax thread/message tables.

Part B — Relay message envelope

Define a shared relay message envelope.

Suggested type:

type OraxRelayMessage = {
  id: string;
  type:
    | "host_connected"
    | "host_disconnected"
    | "action_requested"
    | "action_acknowledged"
    | "action_progress"
    | "action_completed"
    | "action_failed"
    | "approval_requested"
    | "approval_resolved"
    | "ping"
    | "pong";
  userId: string;
  hostId: string;
  threadId?: string;
  actionId?: string;
  sequenceNum: number;
  idempotencyKey: string;
  payload: Record<string, unknown>;
  createdAt: string;
};

Rules:
- Every message needs an id.
- Every action needs an actionId.
- sequenceNum must increase per host/session.
- idempotencyKey prevents duplicate execution.
- Backend must ignore or deduplicate repeated idempotency keys.

Part D — Backend endpoints for web/mobile

Add endpoints:

POST /api/orax/hosts/:hostId/actions
Creates a safe action for the selected desktop host.

Payload:
{
  threadId?: string;
  type: "ping_desktop" | "get_desktop_status" | "list_local_projects";
  payload?: Record<string, unknown>;
}

Response:
{
  action: {
    id,
    status,
    type,
    hostId,
    threadId
  }
}

GET /api/orax/hosts/:hostId/actions
List recent actions for that host.

GET /api/orax/threads/:threadId/messages
If already exists, reuse existing Orax message loading.
If not, add a desktop-thread message route for Phase 2E.

POST /api/orax/relay/events
Fallback endpoint for desktop to post action events if WebSocket is not ready.

Security:
- User must own host.
- Host must not be revoked.
- Only safe action types allowed.
- Reject any action type not in allowlist.
- No shell commands.
- No file writes.
- No git operations.

Part E — Desktop relay client

In artifacts/orax-desktop:

Add:
src/main/relay-client.ts

Responsibilities:
- Connect to backend relay after host registration.
- Authenticate using the same auth token.
- Identify with hostId and installId.
- Maintain connection state:
  - disconnected
  - connecting
  - connected
  - reconnecting
- Reconnect with exponential backoff.
- Send ping/pong.
- Receive actions.
- Deduplicate idempotencyKey.
- Execute only safe Phase 2E actions.
- Emit progress events back to backend.

Part K — Security requirements

- Desktop token must never be logged.
- Relay messages must be scoped to userId and hostId.
- A user cannot send actions to another user’s host.
- Revoked host cannot connect or receive actions.
- Expired/stale host should not be treated as online.
- Idempotency keys must prevent duplicate action execution.
- All unknown action types rejected.
- All messages must be JSON schema validated with zod or equivalent.
