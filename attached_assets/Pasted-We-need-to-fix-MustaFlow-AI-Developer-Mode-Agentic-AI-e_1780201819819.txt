We need to fix MustaFlow AI Developer Mode / Agentic AI execution. Do not redesign the UI first. The issue is not mainly the visual interface. The main problem is that the Developer Mode agent appears to be built, but when the user asks the agent to do something, nothing reliably happens.

Based on the diagnostic report, the frontend workspace, chat panel, agent loop, tool list, SSE events, preview panel, and database tables exist. However, the real runtime/container layer is not being strictly enforced. The system currently allows the agent to run even when the Fly.io/container workspace is missing or not configured. In that case, container operations silently no-op, so the agent may think it created files or ran commands, but the real workspace, terminal, and preview do not update.

This is not acceptable for a Replit-like app builder.

My goal for MustaFlow Developer Mode is:

Users should be able to create their own projects and develop their own apps inside MustaFlow, similar to Replit, with a real AI developer agent that can make changes, run commands, test, iterate, update live preview, and report verified results.

Developer Mode must behave like a real cloud IDE plus AI agent, not just a chatbot.

The correct rule is:

No real runtime/container = no Developer Mode agent execution.

If the runtime is missing or broken, the system must stop and show a clear visible error. It must never pretend the agent worked.

Please fix this in phases.

PHASE 1 — Remove silent no-op behavior from container/runtime tools

Inspect:

artifacts/api-server/src/lib/container.ts
artifacts/api-server/src/lib/agent-loop.ts
artifacts/api-server/src/lib/jobs.ts

Currently, the report says that when FLY_API_TOKEN is missing or container.isConfigured() is false, container operations silently succeed as no-ops.

That must be removed.

Any tool that requires the real workspace/container must throw a clear error if the runtime is unavailable.

Examples of tools that must not silently succeed:

read/write files from real workspace
writeFileToContainer
execInContainer
run_command
install_package / pkg_install
run_e2e
take_screenshot
preview start/restart
container logs
terminal shell
HMR/live preview update

Required behavior:

If container.isConfigured() is false, throw:

ContainerUnavailableError:
“Developer Mode runtime is not configured. The agent cannot edit files, run commands, install packages, test, or update preview until the project container is provisioned.”

Do not return success.
Do not return empty stdout.
Do not let the agent continue as if the tool worked.
Do not let the agent finalize successfully.

PHASE 2 — Add a hard runtime preflight before every Developer Mode agent run

Before the agent loop starts, run a Developer Mode runtime preflight.

Add this to the job start path:

artifacts/api-server/src/routes/messages.ts
artifacts/api-server/src/lib/jobs.ts
artifacts/api-server/src/lib/container.ts
artifacts/api-server/src/lib/provisioning.ts

The preflight must check:

1. Is FLY_API_TOKEN present?
2. Does the project have a valid containerId?
3. Is the container provisioned?
4. Can the system start/wake the container?
5. Can the backend execute pwd inside the project workspace?
6. Can the backend execute ls inside the project workspace?
7. Can the backend create a file named .mustaflow-runtime-test?
8. Can the backend read the test file back?
9. Can the backend delete the test file?
10. Is the preview server reachable or startable?
11. If the project needs database/backend support, is the database connection valid?
12. Is the project marked developer_ready only after the runtime passes?

If the preflight fails, the agent run must not continue.

The task should be marked failed with a clear user-visible message:

“Developer Mode cannot start because the workspace runtime is not ready.
Reason: [specific reason].
Required fix: [specific fix].”

Examples:

Missing FLY_API_TOKEN
Project has no containerId
Container failed to start
Workspace path does not exist
Cannot write to workspace
Preview server failed health check
Database is missing
Auth/session expired

PHASE 4 — Make the agent finalization rule strict

The agent must not be allowed to say “done” unless it has proof.

Update:

artifacts/api-server/src/lib/agent-loop.ts
artifacts/api-server/src/lib/check-profiles.ts

The finalize tool must be blocked unless the agent has verified the work.

For code/build tasks, final success requires:

1. At least one real file read or file tree scan occurred
2. At least one real file change occurred, if the request asked for code changes
3. File changes were written to the real workspace/container
4. Required command/check actually ran, not no-op
5. Typecheck/build/test result is known
6. Preview health was checked when UI/route/page changes were made
7. Final report includes changed files
8. Final report includes commands/checks run
9. Final report includes verification status

Bad final response:

“I updated it. It should work now.”

Correct final response:

“I created src/pages/TestAgentPage.tsx, updated src/App.tsx route, ran typecheck, restarted preview, verified the page loads, and the final check passed.”

If verification fails, the agent must either fix the problem and rerun checks or report the failure clearly.

Final verdict from the diagnostic report:

The Developer Mode architecture is mostly present, but the runtime/container/preview enforcement is broken or degraded. The likely core problem is that Fly.io container configuration is missing or unavailable, and container tools silently no-op. The secondary possible problem is stuck queued runs from advisory locks.

Fix priority:

1. Confirm and configure FLY_API_TOKEN and container provisioning.
2. Remove all silent no-op behavior from container.ts.
3. Add hard runtime preflight before every agent run.
4. Block agent execution if runtime is not ready.
5. Show all errors visibly in the Developer Mode UI.
6. Add stuck-run detection and recovery.
7. Require proof before the agent can finalize.
8. Validate with file creation and preview page tests.

Do not mark this complete until the two minimum working tests pass and the user can see the agent actually create files, run checks, and update the preview.
