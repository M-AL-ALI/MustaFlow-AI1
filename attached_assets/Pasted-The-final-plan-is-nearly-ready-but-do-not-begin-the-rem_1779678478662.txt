1. Do not reuse the existing live development container as the immutable test runtime

The existing `containerId` development container is already connected to live draft editing, terminal actions and AI file synchronization.

If Full App Preview reuses this same container, then:

- the user can start testing snapshot A;
- a file save, Main Agent build, Task Agent Apply or terminal edit can mutate the running container;
- the UI may say snapshot A is being tested while the runtime no longer contains snapshot A.

Required correction:

Add a dedicated Full App Preview/Test container separate from the existing live development container:

- `testContainerId`
- `testContainerUrl`
- `testContainerStatus`
- `runningTestSnapshotId`

Rules:

- Quick Preview and live draft workflows may continue using the existing dev/WebContainer behavior.
- Full App Preview must run only from the immutable Test Candidate snapshot.
- Draft file writes and AI live sync must never modify the test container automatically.
- When draft changes occur, mark the candidate stale, but keep the tested/running snapshot ID for audit and display.
- The user must click `Rebuild Test Preview` to create and run a new immutable candidate.
- Task Agent Apply and Main Agent changes invalidate approval, but must not silently mutate the currently running test candidate.

Required tests:

- A live draft edit does not change files inside the running test container.
- A stale candidate remains identifiable by snapshot ID.
- Approval applies only to `runningTestSnapshotId`.
- A test container can never approve files introduced by live draft synchronization.
