Do not start implementation yet. The plan is almost approved, but the preview-origin design is still not sufficient for real full-app testing.

1. `/p-test/{token}/...` is not a true app origin

A path-based proxy does not correctly support generated apps that use root-relative URLs.

Example:
- iframe loads `https://mustaflow.app/p-test/TOKEN/`
- generated app runs `fetch("/api/users")`
- browser sends request to `https://mustaflow.app/api/users`
- request does NOT reach the generated app container

The same problem affects:
- `/auth/callback`
- `/assets/*`
- cookies
- WebSockets
- service workers
- absolute redirects
- OAuth allowlisted callback URLs

Required correction:

Use a dedicated preview origin per immutable test runtime, such as:

`https://<preview-session>.preview.mustaflow.app/`

or an equivalent isolated preview hostname routed through an authenticated gateway.

Requirements:
- `/` routes to the test container root.
- `/api/*` routes to the generated app backend.
- WebSocket upgrades route to the generated runtime.
- Cookies are scoped to the preview app origin.
- Auth callback URLs can target the preview app origin.
- Root-relative assets and redirects work normally.
- Service-worker scope remains inside the preview origin.
- Raw Fly/container URLs are never exposed publicly.

Access control:
- User starts Full App Preview while authenticated in MustaFlow.
- Backend creates a short-lived preview access session.
- Prefer exchanging a one-time launch token for an HttpOnly, Secure, SameSite cookie scoped to the preview hostname.
- Do not rely on an 8-hour token permanently embedded in the iframe URL, where it may appear in logs, screenshots, referrers or copied links.
- Add `Referrer-Policy: no-referrer` and appropriate `frame-ancestors` protection so only MustaFlow studio can embed the test preview.

Required tests:
- From the preview frontend, `fetch("/api/test")` reaches the generated app backend.
- Root-relative static assets load from the generated app.
- WebSocket connections reach the generated runtime.
- Session cookies remain scoped to the preview app origin.
- Auth callback URLs function on the preview hostname.
- An unauthenticated user cannot access the preview origin.
- A revoked or expired preview session immediately loses access.

3. Production migration policy is still too permissive

A destructive production migration cannot be made safe merely by requiring confirmation.

If the old production app remains live while a destructive migration changes the database, the old live app may already be broken even though `publishedSnapshotId` was not changed.

Required correction for the first release:

- Block destructive production migrations entirely in automatic publish.
- Do not permit `DROP TABLE`, `DROP COLUMN`, destructive renames, destructive type changes, `TRUNCATE`, reset operations or unsupported raw SQL through a confirmation checkbox alone.
- Allow only explicitly validated backward-compatible migrations, or block all production schema-changing publishes until a stronger migration system exists.
- Migration failure must prevent traffic switching, but documentation must state that database rollback is not automatic.

Required tests:
- Destructive migrations cannot be published through the automated flow.
- Unsupported migration SQL blocks publish.
- Allowed additive migration plus healthy deployment can switch traffic.
- Migration failure leaves the previous application version selected, with a clear warning if any database change may already have occurred.
