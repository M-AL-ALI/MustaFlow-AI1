Thank you for the deep audit. Based on your findings, we should NOT build a new user-facing mode.

The correct path is Option B:

Keep the existing AI Builder UI and workspace, but upgrade the backend routing so AI Builder becomes the main Agentic Builder by default.

The audit confirms the platform already has many real foundations:

* AI Builder workspace at /projects/[id]
* Real preview iframe through PreviewTab / PreviewPane
* SSE task streaming
* Real project_files storage
* Real file creation/editing
* Real Plan Mode
* Real task system
* Real Knowledge Vault
* Real checkpoint/rollback
* Real model tiers
* Real deployment/publishing logic
* Real preview error capture
* Real agent-loop.ts with tools
* Real container/database provisioning, but currently not default for normal AI Builder
* Real Developer Mode tools, but these should remain advanced/optional

The problem is not that MustaFlow lacks agentic capability.

The problem is routing and surfacing.

AI Builder currently does not consistently use the strongest agentic path. The true agent-loop.ts, provisioning, command approval, tool narration, mid-run steering, and container-backed workflow are not fully surfaced in the standard Builder chat experience.

So the next phase should be:

Phase 1 — Agentic Default for AI Builder

Goal:
Make the existing AI Builder become the main Agentic Builder without creating a new user-facing mode.

Required changes:

1. Route new AI Builder projects through agent-loop.ts by default
   Do not send normal AI Builder projects to the static/single-shot JSON pipeline when the request requires real app-building.

The AI Builder should use the agent-loop.ts workflow for:

* Full app creation
* Frontend + backend work
* Database work
* Package installation
* Testing
* Debugging
* Preview fixing
* Deployment preparation

2. Auto-provision real runtime for Builder projects
   When a user starts a real app/web project in AI Builder, the system should provision the correct runtime automatically.

Preferred:

* Fly.io container + project database when infrastructure env vars are available

Fallback:

* WebContainer / in-browser runtime when Fly.io or Neon keys are not available

The user should not have to manually choose Developer Mode just to get real agentic behavior.

3. Keep Developer Mode as Advanced View, not the main experience
   Developer Mode can remain a powerful separate route for advanced users.

But for normal users, AI Builder should still be the main experience.

The user should use:

* Chat
* Preview
* Progress stream
* Simple approve/fix/test/publish actions

Developers can still open:

* Files
* Monaco editor
* Terminal
* Git
* Database explorer
* Logs
* Packages
* Resources
* Deployment tools

But the main agentic brain should serve AI Builder first.

4. Surface agent-loop narration inside Builder chat
   The agent already has tool calls and task events. Bring that into the normal AI Builder chat.

The user should see useful progress such as:

* Reading project files
* Creating frontend components
* Installing packages
* Creating backend API
* Updating database schema
* Running tests
* Capturing preview errors
* Fixing missing import
* Retesting
* Checkpoint saved
* Preview updated

Do not bury this only in Developer Mode.

5. Surface command approval inside Builder chat
   The audit says requireCommandApproval exists but is not properly surfaced in the normal AI Builder UI.

Fix this.

When the agent needs approval, show a clear card in the Builder chat:

* What command/action it wants to run
* Why it is needed
* Risk level
* Approve button
* Deny button
* Safer alternative if available

This is very important for non-technical users.

6. Connect preview refresh to file-write events
   The preview should update as the agent works, not only at the very end.

When agent-loop.ts commits a file batch or completes a meaningful step:

* refresh the preview iframe
* capture errors
* stream preview status back to chat
* allow the agent to fix issues

7. Make preview a real testing/staging environment
   The preview must stay real, not fake.

The user should be able to test:

* Buttons
* Forms
* Navigation
* API calls
* Database saves
* Dashboard data
* Login/auth test mode
* Payment test mode when keys exist
* Mobile responsiveness

If something is mock data, label it clearly.

8. Wire mid-run steering to Builder chat
   If steering hints already exist in the agent loop, expose them in AI Builder.

The user should be able to interrupt or steer during a task:

* “Use a cleaner design.”
* “Do not add payment yet.”
* “Make it mobile first.”
* “Stop and show me what you changed.”
* “Use PostgreSQL instead.”
* “Keep the existing dashboard.”

9. Use user_query and request_secret in Builder chat
   The audit says the agent already has user_query and request_secret tools.

Expose these clearly in AI Builder.

If the agent needs clarification, it should ask inside chat.
If the agent needs an API key, it should request it safely inside chat and then resume.

Example:
“The Stripe payment feature needs STRIPE_SECRET_KEY. Please add it here, or I can continue in mock/test mode.”

10. Make the check/finalize loop visible
    The audit says finalize triggers checks and refuses completion when checks fail.

Surface this in Builder chat:

* TypeScript check passed/failed
* ESLint passed/failed
* Playwright smoke test passed/failed
* Server health check passed/failed
* Secret leak scan passed/failed
* What the agent fixed after failure

The agent should not say “done” until checks pass or clearly explain what remains blocked.

11. Preserve checkpoints before risky changes
    Every major phase should create or update checkpoints:

* Before major file overwrite
* Before database migration
* Before variant graduation
* Before deployment
* Before rollback
* After successful build/test cycle

12. Keep one main product experience
    The final user-facing structure should be:

Ora = public consultant / idea helper before login
AI Builder = main Agentic Builder after login
Developer Mode = optional advanced workspace for technical users

Do not create another top-level mode unless absolutely required.

Success criteria for Phase 1:

A user can open AI Builder and type:
“Build me a booking app with login, admin dashboard, and database.”

Then MustaFlow should:

1. Create an agent task.
2. Auto-provision runtime/container/database or use fallback runtime.
3. Use agent-loop.ts, not the static one-shot pipeline.
4. Write real files.
5. Install needed packages if safe.
6. Create frontend.
7. Create backend/API.
8. Create database schema/test data.
9. Start/refresh preview.
10. Capture preview/build/runtime errors.
11. Fix errors automatically when safe.
12. Ask for approval when needed.
13. Run quality checks.
14. Save checkpoint.
15. Show progress and result in Builder chat.
16. Let the user test the real app before deployment.

Please create the implementation plan for Phase 1 only.

Do not rebuild the whole platform.
Do not create a new user-facing mode.
Do not touch unrelated features.
Focus on making the existing AI Builder agentic by default.
