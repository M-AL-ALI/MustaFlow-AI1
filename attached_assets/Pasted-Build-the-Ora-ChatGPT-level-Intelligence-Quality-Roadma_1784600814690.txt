Build the Ora “ChatGPT-level Intelligence & Quality Roadmap” in safe, gated phases.

Goal:
Make Ora closer to ChatGPT as a full intelligent assistant on both website and mobile: smarter routing, better reasoning, stronger file work, better memory, reliable voice, live search, image quality, project organization, transparent outputs, and strict QA gates.

Important:
Do NOT build this as one huge risky commit. Build it phase-by-phase. Each phase must pass the Ora QA/release gate before publish/TestFlight or before moving to the next phase.

Do not bypass the QA gate rules already set up.

GLOBAL NON-NEGOTIABLE RULES

1. Website + mobile parity
Every user-facing Ora feature must work on both website and mobile unless explicitly marked:
- backend-only
- website-only
- TestFlight-required

If mobile needs native code, say “TestFlight required” in the report.

2. Do not regress previous fixes
Do not break:
- Talk to Ora stability
- Talk to Ora tier time-limit behavior
- mobile documentRefs
- uploaded-file editing
- original-file layout preservation
- mobile file View/Download cards
- session recovery
- search/current info
- image generation/editing
- billing/account sync
- App Store compliance
- conversation history
- Back to Ora navigation
- file upload/download/export
- ZIP upload
- PowerPoint reading
- PDF download cards
- Apple Sign in / delete account compliance

3. Feature registry is mandatory
Every new Ora feature or changed Ora surface must update:

scripts/src/ora-stability-gate.ts
ORA_FEATURE_REGISTRY

Each registry entry must include:
- feature name/id
- API surfaces
- website surfaces
- mobile surfaces
- changed-file detection hints
- website manual validation notes
- mobile manual validation notes

If a changed Ora file is not mapped to a registered feature, do not publish and do not submit TestFlight.

4. QA / release gate is mandatory
Before every publish or TestFlight build, run:

pnpm --filter @workspace/scripts run ora-stability-gate -- --profile=release --require-clean --report=tmp/ora-stability-gate-report.md

Required result:
- 0 failed
- 0 warnings
- clean tree
- feature registry passes
- api-server typecheck passes
- website typecheck passes
- mobile typecheck passes
- Ora routing tests pass
- file/chart/export tests pass
- search/current info tests pass
- Talk to Ora tests pass
- website/mobile parity tests pass
- build/lint checks pass

If any automated gate fails:
- do not publish
- do not submit TestFlight
- fix the failure first

5. Manual QA is mandatory after automated gate
After the automated gate passes, complete the manual checklist in:

docs/ora-stability-gate.md

Manual QA must include any changed surfaces:
- website
- mobile/TestFlight
- backend/API
- file upload/edit/download
- voice
- search
- image generation
- billing/account
- history
- memory
- App Store-sensitive flows

6. Report format for every phase
Every phase report must include:
- commit SHA
- changed files
- backend impact
- website impact
- mobile impact
- tests added
- release gate command used
- release gate result
- manual QA result
- TestFlight required or not
- known limitations
- what users should test

7. Real user failures become regression tests
Every issue found by users must become an automated regression test and/or manual gate checklist item.

PHASE 2 — Tool-First Agent Behavior

Ora should not just answer text. It should choose tools.

Before answering, Ora should decide:
- Do I need current web search?
- Do I need to inspect files?
- Do I need to edit an Office file?
- Do I need to create a chart?
- Do I need to generate an image?
- Do I need to ask a clarification?
- Do I need to return a downloadable artifact?

For complex tasks, Ora should internally plan:
1. Understand request
2. Select tool
3. Execute tool
4. Verify output
5. Return answer/file with summary

Rules:
- no fake success
- if tool fails, fail honestly
- preserve user message and context
- preserve documentRefs
- preserve conversationId/projectId
- do not silently switch tools without explanation

Tests:
- tool-required prompts use tools
- no text-only response when a file is requested
- failed tool returns honest error
- retry preserves context
