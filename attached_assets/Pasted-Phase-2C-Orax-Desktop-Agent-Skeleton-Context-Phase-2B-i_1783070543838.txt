Phase 2C — Orax Desktop Agent Skeleton

Context:
Phase 2B is now verified at commit c6083a22. The backend foundation is ready:
- Full 9-table Orax Desktop schema exists.
- Host registration, host CRUD, pairing code, pairing redeem/cancel, and heartbeat routes exist.
- API server typecheck is clean.
- Wiring test is 15/15.
- Ora boundary is clean.

Before starting Phase 2C:
1. Run/apply the Orax Desktop migration in the target environment:
   pnpm --filter @workspace/scripts run migrate-orax-desktop
2. Do not touch Ora, public-ai, AI Builder, credits, project chat, or existing Ora routes.

Goal:
Create the first real Orax Desktop app skeleton. This is not the full coding agent yet. It should establish the desktop runtime, sign-in/auth shell, host registration, heartbeat, pairing code display, local project list placeholder, and permission mode settings.

Build target:
New workspace artifact:
artifacts/orax-desktop

Use:
- Electron + Vite + React
- TypeScript
- Windows-first, but keep platform fields ready for mac/linux
- MustaFlow/Orax branding only

Do not copy OpenAI branding or proprietary implementation.

Required features:

1. Desktop app package
Create a new package at artifacts/orax-desktop with:
- package.json
- tsconfig.json
- vite config
- Electron main process
- preload script
- React renderer
- basic scripts:
  - dev
  - build
  - typecheck
  - lint if local lint setup supports it

The package should be included in pnpm workspace through existing artifacts/* pattern.

2. App layout
Build a simple professional desktop shell:

Left sidebar:
- Orax logo
- Profile section showing signed-in user display name/email
- Projects
- Apps / Connections
- Settings
- Help & Support

Main area:
- If signed out: show sign-in screen
- If signed in but host not registered: show “Set up this computer”
- If host registered: show “Orax Desktop is online”
- Show online/offline status
- Show current device name, OS/platform, app version
- Show permission mode
- Show pairing code / QR payload area
- Show local projects placeholder/list

Important:
Do NOT show password anywhere. The user signs in with the same MustaFlow account, but the app must never display or store raw passwords.

3. Authentication shell
Implement an auth abstraction for desktop sign-in.

Preferred production direction:
- Use the existing MustaFlow/Clerk account.
- Desktop should authenticate through browser/OAuth/device flow, not by collecting raw passwords.
- Store only secure session/token material in the OS credential store or a clearly isolated secure adapter.

For Phase 2C:
- Create the auth adapter interfaces and UI flow.
- If full Clerk desktop OAuth cannot be completed in this pass, add a safe dev-only placeholder behind an explicit development flag.
- No fake production auth.
- No unauthenticated host registration in production code.

Suggested files:
- src/main/auth.ts
- src/main/credential-store.ts
- src/renderer/auth/SignInScreen.tsx

4. Stable install/device identity
Create and persist:
- installId: stable UUID generated once per desktop install
- hostId: returned by backend after registration
- deviceName: OS hostname or editable display name
- platform: windows/mac/linux
- osVersion
- appVersion
- capabilities object

Do not confuse:
- userId = MustaFlow account owner
- installId = stable local app installation ID
- hostId = backend host row ID
- mobileDeviceId = paired mobile/browser device identity

Store installId locally. Store sensitive tokens securely.

5. Register desktop host
Call existing backend endpoint:

POST /api/orax/hosts/register

Payload should include:
- deviceName
- platform
- osVersion
- appVersion
- installId
- publicKey placeholder or generated key if implemented
- capabilities
- metadata

Capabilities for Phase 2C can be:
{
  shell: false,
  filesystem: false,
  git: false,
  github: false,
  browser: false,
  screenshot: false,
  computer_use: false
}

Do not enable shell/filesystem/git execution yet. Phase 2C is registration/pairing skeleton only.

6. Heartbeat loop
After successful registration, start heartbeat:

POST /api/orax/relay/heartbeat

Behavior:
- Send every 30 seconds.
- Update status in UI.
- If heartbeat fails, show offline/reconnecting state.
- Use exponential backoff after repeated failures.
- Stop heartbeat on sign-out or app shutdown.

7. Pairing code display
Implement desktop-side pairing code generation:

POST /api/orax/pairing-codes

UI should show:
- 6-character manual code
- QR payload text area or QR placeholder
- expiry countdown, 10 minutes
- refresh code button
- cancel code button using:
  DELETE /api/orax/pairing-codes/:code

Do not build mobile scan flow in this phase. That is Phase 2D.

8. Permission mode settings
Expose permission mode selector in Settings:

Modes:
- read_only
- ask_everything
- ask_risky default
- trusted_project
- full_access
- custom

Persist mode to backend with:

PATCH /api/orax/hosts/:hostId

Important:
Even if UI lets user select modes, Phase 2C must not execute commands yet. Execution enforcement comes later.

9. Local project list placeholder
Add local project management shell:
- “Add local folder” button
- Use Electron file/folder picker to select a folder
- Store selected folders locally for now
- Show project display name and path
- Allow remove from local list

Do not sync projects to backend yet unless the backend project routes already exist and are intentionally included. The Phase 2B schema has orax_projects, but project API routes are not required for Phase 2C unless explicitly scoped.

10. API client
Create a desktop API client:
- Base URL from env/config, e.g. ORAX_API_BASE_URL
- Auth header support
- Typed helper methods:
  - registerHost
  - updateHost
  - createPairingCode
  - cancelPairingCode
  - heartbeat

All logs must redact tokens/secrets.

11. IPC boundary
Use typed IPC between Electron renderer and main process.

Suggested channels:
- auth:getSession
- auth:startSignIn
- auth:signOut
- host:register
- host:getStatus
- host:updatePermissionMode
- pairing:create
- pairing:cancel
- project:addLocalFolder
- project:listLocalFolders
- project:removeLocalFolder
- app:getVersion
- logs:getRecent

Renderer must not directly access Node filesystem APIs.

12. Safety rules
Phase 2C must NOT:
- run PowerShell commands
- edit files
- run git commands
- push to GitHub
- create PRs
- access Ora/public-ai routes
- touch credits or billing logic
- touch AI Builder
- touch project chat

This phase only prepares the trusted desktop host connection.

13. Tests / wiring guards
Add or update tests to verify:
- artifacts/orax-desktop exists
- Electron main/preload/renderer files exist
- host registration endpoint is referenced
- heartbeat endpoint is referenced
- pairing code endpoint is referenced
- permission modes are present
- no Ora/public-ai/project chat imports or route calls exist in Orax Desktop code
- no password display/storage strings exist
- renderer uses IPC, not direct filesystem access
