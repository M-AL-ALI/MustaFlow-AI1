I noticed there is currently no visible button to start talking by voice with Ora. We need to make sure this is included in the voice phase and not forgotten.

Again: do not mix this into Phase 3 dataset work unless I explicitly approve it. Finish and validate Phase 3 first. But please add this as a required scope item for the upcoming Ora voice phase.

Voice requirements:

1. Microphone button in Ora UI
    Add a clear microphone button inside:

* Ora Lens panel
* Ora Bubble drawer
* mobile Ora bottom sheet/drawer

The visitor should easily see they can talk to Ora.

Additionally, Ora should support natural voice conversation behavior:

* detect when the user has finished speaking and then respond
* automatically stop listening after a reasonable period of silence and process the message
* if the user interrupts while Ora is speaking, immediately stop playback and switch back to listening mode
* prioritize the user’s speech whenever both user and assistant audio overlap
* only generate a response after the user’s current utterance is complete

2. Voice-to-text transcript must appear in the message thread
    When the visitor speaks, the spoken words must be transcribed and inserted into the Ora conversation as a normal user message.

Example:

Visitor speaks: “Can MustaFlow build a towing app?”

Message thread should show:

User: “Can MustaFlow build a towing app?”

Then Ora replies normally in the same thread.

3. Ora response must also appear as normal assistant message
    Ora’s answer must show in the chat thread as text, even if text-to-speech is enabled.

Example:

Ora: “Yes, MustaFlow can help you plan and build a towing marketplace…”

4. Optional speech playback
    Ora may also speak the response aloud, but the text answer must always be visible in the message thread.

Do not make voice audio-only.

5. Live transcript behavior
    While the visitor is speaking, show:

* “Listening…”
* live/interim transcript if browser supports it
* final transcript before sending, or auto-send after silence if designed that way
* stop/cancel button

Recommended behavior:

* user taps microphone
* Ora starts listening
* transcript appears live or after speech ends
* user can review/edit transcript if possible
* transcript is sent as a normal message
* Ora responds in the same chat thread
* optional play button reads Ora’s reply aloud

6. Multilingual voice support
    Voice must respect language behavior:

* detect spoken language when possible
* if the visitor speaks Arabic, transcript should be Arabic and Ora should reply in Arabic
* if Spanish, transcript Spanish and reply Spanish
* if English, transcript English and reply English
* if user selected a language manually, set the recognition language accordingly

7. Session memory
    Voice messages must be part of the same session memory as typed messages.

If the visitor speaks something, refreshes the page, and the session is still active, the transcript should remain in the conversation history just like typed messages.

8. Privacy and safety
    Do not permanently store voice audio for anonymous visitors.

Do not log raw audio.

Do not log transcript text.

Do not send voice content to Builder or project memory.

Only temporary in-session memory should keep the transcript.

9. Fallback behavior
    If browser-native speech recognition is unavailable:

* show a clear message: “Voice input is not supported in this browser. You can still type your message.”
* optionally use API transcription fallback if approved and rate-limited

10. Final requirement
    Voice conversation must feel natural, but the chat thread must remain the source of truth.

Everything spoken by the visitor should become a visible user message.

Everything Ora says should become a visible assistant message.

Audio playback is optional, but the transcript/message thread is required.

Please acknowledge this voice scope as a future required phase item, but do not start implementing it until I approve that phase.
