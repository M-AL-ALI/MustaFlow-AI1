Start the next task as Ora Production Safety Wave 1D — Multi-Instance Spend Cap Enforcement.

Reason:
Wave 1C made spend tracking durable and restart-safe, but cap enforcement still reads the local in-memory counter. The DB upsert is atomic, but if multiple API instances run at the same time, each instance can think it is under the cap while the global DB total has already crossed the cap.

Goal:
Make spend cap enforcement safer across multiple API instances without rebuilding the whole system.

Preferred approach:
Use a lightweight DB resync/check strategy before allowing expensive requests.

Implementation options:

1. Preferred simple option:
    * Periodically resync in-memory counters from the DB.
    * Also force a DB read/check when usage is close to a cap threshold, such as 80% or higher.
    * This avoids a DB read on every request but closes the biggest multi-instance overspend risk.
2. Stronger option:
    * Move cap enforcement fully to Postgres for all cap checks.
    * Check DB totals before allowing a request.
    * Use atomic updates or transaction-safe logic to prevent cap bypass.
    * This is safer but more complex.

Requirements:

1. Keep the existing in-memory fast path for normal low-usage requests.
2. Add DB-backed verification when close to cap.
3. Ensure global cap, authenticated per-user cap, and anonymous per-IP cap are checked against durable DB totals before allowing high-risk requests.
4. Avoid excessive DB reads for every normal request.
5. If DB is unavailable:
    * log ora_spend_ledger_degraded
    * continue using in-memory caps if that is the approved fail-open behavior
    * do not crash the request path
6. Add structured logs when a DB resync/check changes the cap decision.
7. Add tests for:
    * DB total already over global cap while memory is under cap
    * DB total already over user cap while memory is under cap
    * DB total already over anonymous IP cap while memory is under cap
    * close-to-cap forces DB verification
    * low-usage requests do not force DB verification every time
    * DB unavailable falls back safely and logs degraded warning
    * E2E bypass does not affect production
8. Quality gate must pass.
9. Ora isolation must remain passing.
10. Push all changes to GitHub after completion.

Acceptance:
Wave 1D is complete when multi-instance overspend risk is reduced by DB-backed verification, with tests proving DB totals can block requests even when local memory is stale.
