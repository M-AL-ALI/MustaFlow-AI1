Next Orax parity task: make /plan behave like real Codex-style plan mode on both website and mobile.

Current state:
- /plan exists as a slash command.
- Website and mobile now show the active Goal / Plan mode strip above the composer.
- The strip is verified and wiring tests pass.
- But /plan is mostly visual/thread metadata right now. The runner still needs to respect plan mode as a real execution mode.

Goal:
When the user sends /plan or uses Plan mode, Orax should not jump straight into implementation/draft patch behavior. It should first inspect repository context, produce a clear implementation plan inline in the chat, then stop and wait for the user to continue/approve before making changes.

Required behavior:
1. Backend:
   - Persist plan mode on the Orax task result, e.g. result.activePlan or result.executionMode = "plan_first".
   - The Orax runner must detect this mode.
   - In plan mode, the runner should:
     - inspect needed repository files,
     - summarize relevant findings,
     - generate a concise step-by-step implementation plan,
     - write that plan into the Orax task thread,
     - update checkpoint/next action,
     - stop before draft patch, sandbox, PR, or code-changing actions.
   - It should only proceed to implementation after the user taps Continue or sends a clear command like “continue”, “implement it”, or “start implementation”.

2. Inline response quality:
   - Do not show internal workflow/status dumps.
   - Do not show artifact counts, approval IDs, checkpoint spam, or “Phase 4B” language.
   - The assistant message should feel Codex-like:
     - brief acknowledgement,
     - what it inspected,
     - proposed plan,
     - next action button/card: “Start implementation” or “Continue”.

3. Website:
   - The existing active Plan mode strip should stay above the composer.
   - When a plan is ready, the inline suggestion/action should say “Start implementation” or “Continue”.
   - No extra dashboard panels or workflow-control sections should appear in the normal chat flow.

4. Mobile:
   - Mirror the same behavior exactly.
   - The same Plan mode strip should remain above the composer.
   - The same inline “Start implementation” / “Continue” action should appear in the thread.
   - No Ora files or Ora chat behavior should be touched.

5. Safety:
   - Orax must remain separate from Ora.
   - Do not touch Ora, AI Builder, public-ai chat, credits, or project chat.
   - Do not copy OpenAI branding or proprietary implementation.
   - Functional parity only, under MustaFlow AI/Orax architecture.

6. Tests and wiring:
   - Add/update API Orax tests for:
     - /plan persists plan mode.
     - plan-mode runner stops after producing a plan.
     - plan-mode runner does not create draft patches before user continue.
     - follow-up continue exits plan-only stop and proceeds to implementation.
   - Add/update wiring tests for website and mobile:
     - plan strip still exists.
     - “Plan mode” state is surfaced.
     - “Start implementation” or equivalent CTA is wired inline.
     - no Ora boundary strings appear.
   - Run:
     - pnpm --filter @workspace/api-server run typecheck
     - pnpm --filter @workspace/mustaflow run typecheck
     - pnpm --filter @workspace/mustaflow run lint -- --max-warnings 0
     - pnpm --filter @workspace/ora-mobile run typecheck
     - Orax wiring test
     - API Orax test

Expected result:
Orax Plan mode should feel like Codex: the user asks for a plan, Orax studies the repo, writes a useful plan inline, then waits before making code changes. Website and mobile must stay synced.
