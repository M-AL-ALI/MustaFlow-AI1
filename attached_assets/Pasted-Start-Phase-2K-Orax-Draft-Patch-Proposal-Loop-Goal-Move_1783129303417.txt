Start Phase 2K — Orax Draft Patch Proposal Loop

Goal:
Move Orax from “inspect files + suggest plan” into the next Codex-style step: produce a reviewable draft patch proposal from the selected/read files, but do not write files yet.

Important:
Do not touch Ora, public-ai chat, AI Builder, credits, or normal Ora project chat.
Only work inside Orax desktop / Orax backend / Orax website / Orax mobile wiring.

What & Why:
Phase 2J lets the desktop agent inspect a local project, select relevant files, read safe previews, and create a suggested plan. The next missing Codex-like behavior is the “here is the change I would make” step.

Orax should now be able to create a draft patch preview inline in the thread, using the files it safely read. This should feel like Codex: user asks for a coding task, Orax inspects context, reads files, proposes a plan, then prepares a patch preview for review. It must not write to disk until a later approval phase.

Done Looks Like:
- Desktop receives a `draft_project_patch` action.
- Desktop uses Phase 2J `fileReadSummary` / selected file previews to build a draft patch proposal.
- No actual source files are modified in Phase 2K.
- Patch proposal is returned to backend as structured data.
- Backend writes an inline `project_patch_drafted` assistant message to the Orax thread.
- Website renders patch preview inline, not as a dashboard/log wall.
- Mobile can fetch and display the same thread message safely.
- All patch paths are relative and validated under the local project root.
- Secret files, blocked files, absolute paths, `..`, symlinks, and outside-root paths remain blocked.
- No shell execution for draft generation.
- Wiring tests cover backend, desktop, website, mobile, and Ora isolation.

Implementation Steps:

1. Add desktop patch drafter
Create:
`artifacts/orax-desktop/src/main/project-patch-drafter.ts`

Responsibilities:
- Input: localPath, userMessage, selectedFiles/fileReadSummary/suggestedPlan.
- Output: structured draft patch object.
- Keep it deterministic for now. No AI call yet unless existing architecture already supports safe server-side AI generation.
- Generate a reviewable patch proposal with:
  - summary
  - changedFiles[]
  - per-file intended operation: update/create/delete, but Phase 2K should only propose update/create unless delete is explicitly safe and approval-gated later
  - unifiedDiffPreview or structured hunks
  - risks[]
  - verificationPlan[]
- Do not write files.
- Do not use shell.
- Do not call process.cwd().
- Validate every path with the same safety rules as project-file-reader.

2. Add relay action handling
Update:
`artifacts/orax-desktop/src/main/relay-client.ts`

Add support for:
`draft_project_patch`

Flow:
- Validate payload includes projectId, threadId, executionSourceId, sourceLocalPath, userMessage.
- Verify `.orax/project.json` binding matches projectId / executionSourceId.
- Reuse selected/read file context from payload when available.
- If missing, safely re-run selector + reader.
- Call `draftProjectPatch(...)`.
- Post `running`, then `completed` with:
  - draftPatch
  - selectedFiles
  - warnings
  - suggestedPlan
- On failure, post `failed` with redacted path-safe error.

3. Add backend action queue path

or existing Orax project thread continue route.

After project files are inspected/read:

- Preserve chat_only behavior: if no desktop/local source is online, return a clear inline blocker instead of pretending to run.
