Task: Verify and harden Ora cross-platform account consistency before any build

Goal:
Before TestFlight/native build, prove that Ora Website and Ora Mobile are using the exact same account identity and shared data:
email, Clerk user ID, plan/tier, projects, conversations, recent history, memories, profile, support tickets, usage, and feature access.

Important:
Do not run EAS/TestFlight yet.
This task is verification + diagnostic hardening only.

What is already wired correctly:
1. Website auth:
   - Website uses Clerk.
   - Website authFetch attaches Authorization: Bearer <Clerk token> for same-origin /api calls.
   - Website also keeps credentials: include as cookie fallback.

2. Mobile auth:
   - Ora Mobile uses @clerk/expo.
   - app/_layout.tsx configures ClerkProvider with the same publishable key/proxy pattern.
   - (home)/_layout.tsx registers getToken() into the mobile API client.
   - artifacts/ora-mobile/lib/api.ts attaches Authorization: Bearer <Clerk token> to API requests.
   - Mobile API base defaults to https://www.mustaflow.com unless EXPO_PUBLIC_DOMAIN overrides it.

3. Server identity:
   - api-server uses clerkMiddleware().
   - protected routes run attachUser.
   - attachUser resolves req.userId from Clerk sessionClaims.userId or auth.userId.
   - Public Ora routes also resolve signed-in users through resolveAuthedOraUser(req), using the same Clerk userId.
   - Therefore the source of truth is Clerk userId, not device, not email, and not the anonymous ora-session cookie.

4. Shared Ora data endpoints:
   Website and mobile both use the same backend endpoints:
   - /api/ora/conversations
   - /api/ora/conversations/:id
   - /api/ora/conversations/:id/messages
   - /api/ora/projects
   - /api/ora/memories
   - /api/ora/profile
   - /api/billing/subscription
   - /api/public-ai/session
   - /api/public-ai/usage
   - /api/help/support/...
   - /api/public-ai/realtime/session
   - /api/public-ai/realtime/diagnostics

5. Server-side ownership filters:
   - Conversations are filtered by ora_conversations.userId = req.userId.
   - Projects are filtered by ora_projects.userId = req.userId.
   - Memories are filtered by knowledge_entries.userId = req.userId, scope="user", origin="ora", archivedAt null.
   - Profile is stored by ora_profiles.userId.
   - Billing subscription is stored by user_subscriptions.userId.
   - Support ticket routes resolve the user through Clerk and should be user-owned.
   - This is the correct architecture for website/mobile data sharing.

Known nuance:
Email alone is not enough to prove account equality. The real identity key is Clerk userId. If the same email somehow resolves to a different Clerk user on mobile vs website, data will not match. Diagnostics must show a safe Clerk user fingerprint on both platforms.

Required work:
1. Add a single server-side account consistency endpoint.

Create a protected endpoint, for example:
GET /api/ora/account-consistency

It should require Clerk auth and return privacy-safe diagnostic data:
{
  ok: true,
  user: {
    userIdHash: "first 12 chars of sha256(req.userId)",
    clerkUserIdLast4: optional last 4 chars only,
    email: primary email if safely available from Clerk, or null
  },
  api: {
    environment: production/staging/dev if available,
    host: request host
  },
  billing: {
    billingTier,
    sourceTier,
    status,
    isSuperuser,
    currentPeriodEnd,
    cancelAtPeriodEnd
  },
  chatSession: {
    tier,
    isPaid,
    messageLimit,
    imageLimit,
    resetsAt
  },
  counts: {
    conversations,
    projects,
    userLevelMemories,
    projectMemories,
    assets,
    supportTickets
  },
  latest: {
    latestConversationId,
    latestConversationTitle,
    latestConversationUpdatedAt,
    latestProjectId,
    latestProjectName,
    latestMemoryId,
    latestMemoryTitle
  }
}

Rules:
- Do not return raw req.userId unless this is explicitly admin-only.
- Prefer userIdHash so website and mobile can compare identity without exposing the full Clerk ID.
- Do not return private message contents.
- Do not return memory content, only counts/title/id.
- All counts must be filtered by req.userId.
- Include enough detail to verify website and mobile are seeing the same account.
