## Answers to your three questions

### 1. Edit history layout

Use grouped edit history under the parent image.

Edited images should not appear as random unrelated images only. They should show as an edit thread:

Original image
→ Edit 1
→ Edit 2
→ Edit 3

In the grid, it is okay to show edited images as normal cards, but each edited image must show:

* “Edited” label
* parent image reference
* “View history” option

Recommended DB structure:

* `parent_image_id` — immediate parent
* optionally later `root_image_id` — original root image for easier grouping

For Phase 9A-2, `parent_image_id` is enough, but design so `root_image_id` can be added later if needed.

### 2. Upload size limit

10 MB is approved for Phase 9A-2.

Allowed upload types:

* PNG
* JPG / JPEG
* WEBP

Required upload validation:

* MIME type check
* magic-byte validation
* max file size 10 MB
* max image dimensions if practical
* safe filename handling
* strip EXIF/metadata before storage if possible
* convert stored upload to WebP
* create thumbnail
* store original uploaded asset as a generated_images row with status `completed`

If file is too large or unsupported, return a clear user-friendly error.

### 3. Edit button placement in chat

Show the Edit button directly on the completed image card, but do not show the edit text box until the user clicks Edit.

So the card actions should be:

* Download
* Edit
* Delete if supported
* Use in Project — Coming in Phase 9A-3

When user clicks Edit:

Show an inline prompt under the image card:

“Describe your change…”

Then user submits the edit instruction.

The edited result should create a new image job and then a new image card with an “Edited” label.

## Important backend requirements

Add:

`POST /api/images/upload`

Purpose:

* upload a user-owned source image
* validate file type/size
* store to R2 under uploaded image prefix
* create DB row
* return image metadata

Add:

`POST /api/images/:id/edit`

Purpose:

* validate ownership of source image
* validate edit instruction
* run safety check before credits
* call provider edit endpoint
* store edited result to R2
* create new DB row with `parent_image_id`
* preserve original image
* return job/image status

## DB changes

Add at minimum:

```sql
ALTER TABLE generated_images
  ADD COLUMN parent_image_id INTEGER REFERENCES generated_images(id);
```

Also consider adding now if easy:

* `source_type` — generated / uploaded / edited
* `edit_instruction`
* `original_file_url` or source reference if needed
* `root_image_id` optional later

Do not overcomplicate it, but avoid losing lineage.

## Provider requirement

Before implementation, verify the provider supports the exact image edit endpoint and required input format.

Do not assume the same generate endpoint works for editing.

Confirm:

* model supports editing
* image input format accepted
* uploaded image is sent server-side only
* provider key stays server-side
* no image base64 is logged
* errors are handled safely

## Storage requirement

Use R2 for uploaded and edited images.

Suggested key patterns:

* generated images: `generated-images/{imageId}/full.webp`
* uploaded images: `uploaded-images/{userId}/{imageId}/full.webp`
* edited images: `edited-images/{userId}/{imageId}/full.webp`

Keep thumbnails too:

* `thumb.webp`

Do not store base64 in DB.

## Credits

Upload should be free.

AI edit should cost credits:

* standard edit = 3 credits
* high edit = 6 credits

Safety-blocked edit:

* no provider call
* no credits deducted

Provider/system failure:

* refund credits

Successful edit later deleted:

* no refund
