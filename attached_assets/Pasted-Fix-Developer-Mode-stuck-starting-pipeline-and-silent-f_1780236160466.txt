Fix Developer Mode stuck-starting pipeline and silent failure modes.

The investigation confirmed the root cause. Developer Mode is not failing because of the UI design. It is failing because the container/runtime start pipeline and agent preflight pipeline do not reliably write failure state back to the database or frontend.

Current confirmed problems:

1. POST /api/projects/:id/container/start returns immediately with:
    { containerStatus: “starting” }
2. The real provisioning/start work runs async through setImmediate.
3. If async provisioning fails because of missing FLY_API_TOKEN, missing containerId, Fly.io API error, workspace failure, or preview failure, the failure is only logged or swallowed.
4. The DB is not updated to failed.
5. The frontend keeps polling every 5 seconds forever.
6. The UI stays stuck on:
    * “Starting…”
    * “Container starting…”
7. The agent message flow fails because runAgenticPreflightGate in jobs.ts rejects when the container is not ready.
8. The frontend receives a generic error:
    “Failed to send message. Please try again.”
9. The useful container_unavailable event is emitted only into the task event stream, but the SSE stream only opens after taskId is returned. If /messages fails before returning taskId, the frontend never sees the real error.

This must be fixed now.

Do not redesign Developer Mode UI. Fix the execution pipeline.

Required backend fixes:

1. Fix /api/projects/:id/container/start

Files to inspect and patch:

* artifacts/api-server/src/routes/containers.ts
* artifacts/api-server/src/lib/provisioning.ts
* artifacts/api-server/src/lib/container.ts
* artifacts/api-server/src/lib/event-bus.ts
* artifacts/api-server/src/routes/events.ts
* DB schema for projects/container status

The start endpoint must no longer leave the project stuck in “starting.”

Required behavior:

When container start begins:

* Set container_status = “starting”
* Set provisioning_status = “starting” or “provisioning”
* Set container_started_at = now()
* Clear previous container_error
* Emit event: container.starting

When async start succeeds:

* Set container_status = “running”
* Set provisioning_status = “ready”
* Set developer_ready = true, if all runtime health checks pass
* Set container_ready_at = now()
* Clear container_error
* Emit event: container.ready

When async start fails:

* Set container_status = “failed”
* Set provisioning_status = “failed”
* Set developer_ready = false
* Set container_error = specific failure reason
* Set container_failed_at = now()
* Emit event: container.failed
* Do not leave status as “starting”

Required failure reasons must be specific:

* missing_fly_api_token
* missing_container_id
* fly_api_error
* container_start_timeout
* workspace_not_found
* workspace_not_writable
* preview_start_failed
* unknown_container_start_error

Do not hide the real cause behind generic “starting.”

2. Add try/catch around the async setImmediate provisioning work

The current issue is that /container/start responds before async provisioning finishes. That is fine, but the async code must always write a terminal state.

Required pattern:

setImmediate(async () => {
try {
emit container.starting
update DB to starting
start/provision container
run runtime health check
update DB to running/ready
emit container.ready
} catch (error) {
update DB to failed with clear reason
emit container.failed
log structured error
}
})

There must be no async branch where the DB remains stuck as starting.

3. Add container start timeout

Developer Mode must never show “Starting…” forever.

Add a timeout, for example 90–120 seconds.

If the container does not reach ready before timeout:

* Set container_status = “failed”
* Set provisioning_status = “failed”
* Set container_error = “container_start_timeout”
* Emit container.failed
* Frontend must stop infinite polling and show retry/recover actions

4. Add runtime health check after container start

Container “running” is not enough. Developer Mode needs a usable workspace.

After container starts, run:

* pwd
* ls
* write .mustaflow-runtime-test
* read .mustaflow-runtime-test
* delete .mustaflow-runtime-test
* preview health check, if preview is expected

Only mark Developer Mode ready after this passes.

If it fails, set container_status/provisioning_status to failed with the specific reason.

* artifacts/api-server/src/lib/jobs.ts
