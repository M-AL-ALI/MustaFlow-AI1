Let’s start Phase 2A: TypeScript Repair Loop.

Phase 1 Agentic Container Pipeline / Runtime Stabilization is complete at checkpoint a6750380. Do not reopen the Fly/autostop infrastructure issue unless a new test proves it regressed.

Now focus only on the TypeScript/code-quality repair loop.

Problem:
The agentic pipeline can now run end-to-end, but the generated code may still contain TypeScript errors. The quality gate catches the errors, but the task may still commit and complete in a way that can look like success to the user.

That is not acceptable for MustaFlow AI Builder.

Goal:
When TypeScript/build/quality-gate errors are found, the agent should automatically attempt a repair cycle before finalizing the task.

If the repair cannot fully fix the issue within the allowed retry limit, the task should clearly show:

“Completed with errors”

not clean success.

Required behavior:

1. Quality gate failure must feed back into the agent
    When the quality gate catches TypeScript/build errors, send the actual error output back into the agent loop as repair context.

The repair context should include:

* check name
* command that failed
* relevant error output
* files likely involved
* previous files changed
* instruction to make the smallest safe fix

2. Add controlled retry limit
    Do not allow infinite loops.

Recommended:

* Max 2 repair attempts for Eco/Power
* Max 3 repair attempts for Pro
* Max 1 repair attempt for Lite

If retries are exhausted, stop and report clearly.

3. Repair before final commit when possible
    Preferred behavior:

* Agent writes files
* Quality gate runs
* If TypeScript/build fails, agent repairs
* Quality gate reruns
* If passed, commit/version as successful
* If failed after retry limit, commit only if safe and label as completed_with_errors

4. Do not hide errors from users
    The Builder chat final report must show:

* Checks passed
* Checks failed
* What the agent tried to fix
* Whether the final app is safe to preview/test
* Remaining blockers
* Suggested next action

5. Do not call a failed validation clean success
    Add or reuse a status such as:

* completed
* completed_with_errors
* failed
* needs_user_action

If validation_status = failed, the UI must not show a clean success message.

6. Show repair attempts in Builder timeline
    The live Builder chat timeline should show:

* “TypeScript check failed”
* “Repairing TypeScript errors”
* “Updated affected files”
* “Running checks again”
* “TypeScript check passed”
    or
* “Repair attempts exhausted — user review needed”

7. Use minimal safe patches
    The repair loop should avoid rewriting the entire app unless necessary.

Repair instructions to the agent:

* Fix only the files related to the error.
* Preserve existing working UI.
* Do not remove features to make checks pass.
* Do not delete unrelated code.
* Do not bypass TypeScript by using any everywhere.
* Do not disable strict checks unless explicitly approved.

8. Protect the preview/deployment gate
    If checks fail:

* Preview can still show if runnable, but clearly label “Preview has validation errors.”
* Deployment must remain blocked unless the user explicitly accepts risk and the platform policy allows it.
* Production publish should not proceed with critical TypeScript/build failures.

9. Key files to inspect
    Please audit and modify only what is needed.

Likely files:

* artifacts/api-server/src/lib/agent-loop.ts
* artifacts/api-server/src/lib/quality-gate.ts
* artifacts/api-server/src/lib/jobs.ts
* any task report/status UI components that display validation result
* any schema/type files needed for completed_with_errors or repair metadata

10. Acceptance test
    After implementation, run a controlled test where the generated app intentionally has a TypeScript error.

The test must prove:

* TypeScript check fails
* Error is passed back to the agent
* Agent attempts repair
* Files are updated
* TypeScript check reruns
* Final task status is either passed after repair or completed_with_errors after retry limit
* Builder chat clearly shows the repair attempts and final validation state
