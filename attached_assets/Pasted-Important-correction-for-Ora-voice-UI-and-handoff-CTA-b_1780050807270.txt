Important correction for Ora voice UI and handoff CTA behavior.

The current implementation mixed two separate features together. Please correct this.

There must be TWO different voice experiences:

1. Mic / Dictation Mode
2. Ora Voice Conversation Mode

They are not the same feature.

Current issue shown in screenshot:
The premium voice orb replaced the normal mic behavior in the input area. This makes it look like a voice-mode/voicemail button, but the expected mic feature should still be available as a simple dictation control.

Also, the “Ready to build this? Continue in Builder” card is showing too aggressively after a simple greeting like “Hello.” That is wrong. Visitors do not need to see Builder CTA while just chatting or talking casually.

Please fix both issues.

Part 1 — Restore the normal mic / dictation feature

Return the normal microphone/dictation behavior in the message composer.

Expected behavior:

* user taps mic
* Ora listens
* live/interim transcript appears
* final transcript lands in the text box/composer
* user can review/edit transcript
* user manually presses Send
* transcript becomes a normal user message
* Ora replies as normal assistant message
* no automatic spoken reply required
* TTS remains off unless user manually enables read-aloud

This should be the normal mic button inside the input/composer area.

Recommended composer order:

* attachment button
* normal microphone/dictation button
* text input
* send button

Do not remove this normal mic behavior.

Part 2 — Add separate Ora Voice Conversation Mode

The premium circular voice orb should become a separate “Ora Voice Conversation Mode” feature, not the replacement for the normal mic button.

This feature is for natural voice conversation.

Expected behavior:

* user taps “Talk with Ora” or the premium voice orb
* Ora enters Voice Conversation Mode
* user speaks naturally
* transcript appears in the message thread
* Ora can auto-send after silence or when user stops talking
* Ora replies by sound automatically
* Ora’s spoken reply also appears as normal assistant text in the thread
* user can interrupt Ora while she is speaking
* if user starts talking, Ora stops speaking and starts listening
* user can exit Voice Conversation Mode anytime
* transcript/message thread remains the source of truth

This is different from the mic/dictation feature.

Voice Conversation Mode should feel like a live conversation, while the normal mic button should feel like speech-to-text dictation.

Normal mic/dictation button:

* stays inside the input bar beside the attachment button

Voice Conversation Mode button:

* should be separate and more premium
* can appear in the Ora header, near the Dynamic Atom, or as a separate “Talk with Ora” pill/button

Recommended UI:

* attachment button
* small mic/dictation button
* text box
* send button

This makes the two features clear.

When Voice Conversation Mode is active, show a clear state panel:

* “Voice Mode active”
* “Ora is listening…”
* live waveform
* transcript preview
* “Ora is speaking…” when replying

Voice Mode should auto-play Ora’s response while this mode is active.

Important:
TTS should still default off for normal typed chat.
But inside Voice Conversation Mode, automatic spoken replies are expected because that is the point of the mode.

Current bad example:
User: “Hello”
Ora: “Hello — how can I help?”
Then the Builder CTA appears.

This is wrong.

Please update CTA logic.

Show Builder CTA only when there is clear build/app intent, such as:

* user asks to build an app
* user asks if MustaFlow can build something
* user discusses app idea/planning
* user asks to continue into Builder
* user uploads design/image/dataset/document and asks to build from it
* Ora gives an app plan or build recommendation

Do NOT show Builder CTA for:

* hello / greetings
* casual conversation
* personal advice

* voice testing
