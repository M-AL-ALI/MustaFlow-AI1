Corrections before coding:

1. Use browser-native voice first

This is approved.

But do not overpromise browser support. Browser SpeechRecognition support varies by browser, OS, and device.

Please implement feature detection and graceful fallback instead of assuming all Chrome/Safari/mobile browsers support every language.

2. Start with native browser voice only unless API fallback is truly needed

The plan includes backend routes:

* /api/public-ai/transcribe
* /api/public-ai/tts

Please treat these as optional fallback routes.

Recommended implementation order:

Voice-A:

* browser-native SpeechRecognition / webkitSpeechRecognition
* browser-native speechSynthesis
* no new backend routes yet unless needed
* transcript in message thread
* TTS playback optional
* full UI states

Voice-B:

* API transcription fallback only if native support is not good enough
* API TTS fallback only if browser speechSynthesis is not good enough
* add strict rate limits before enabling fallback publicly

Do not add backend voice routes unless you can prove they are necessary and safe.

3. Auto-send vs review-before-send

Default should be review-before-send, not auto-send.

Recommended behavior:

* user taps mic
* Ora listens
* transcript appears live/interim
* final transcript lands in the text box
* user can edit or press send
* optional setting later: auto-send after silence

Why: this is safer, avoids sending bad transcriptions, and is better for multilingual users when browser recognition makes mistakes.

You may include an auto-send option later, but do not make it the default until tested.

4. Transcript must become the source of truth

Final voice transcript must be treated exactly like typed text.

Required behavior:

* transcript appears in the text box or message thread
* when sent, it becomes a normal user message
* Ora reply becomes a normal assistant message
* sessionStorage stores the text transcript like any typed message
* refresh restores the transcript text if the session is still active
* no audio-only conversation

5. Interruption behavior

Approved, but implement carefully:

* if Ora is speaking and the user taps the mic, stop playback immediately
* if user starts typing while Ora is speaking, stop playback
* if user presses stop, stop playback/listening
* do not start a new AI response until the final transcript is confirmed/sent

6. Multilingual voice behavior

Approved, but with realistic fallback language.

Implement:

* selected language maps to recognition language when possible
* Auto Detect uses browser default/auto behavior when supported
* Arabic, English, Spanish, French should be attempted
* if recognition language fails, show friendly fallback
* text response must still follow Ora’s existing multilingual behavior

Do not claim perfect spoken-language detection.

Use wording like:

“Voice language support depends on your browser/device. You can still type in any supported language.”

7. Privacy

* do not log transcripts
* do not send audio/transcripts to Builder/project memory
* only text transcript is temporarily stored in sessionStorage after user confirms/sends it

Ora should become more than a basic public AI assistant. Ora should feel like MustaFlow’s intelligent companion, expert consultant, troubleshooting partner, and professional helper for visitors.

* respectful
* calm
* patient
* professional
* encouraging
* trustworthy
* helpful like a smart friend
* clear like a consultant
* capable like an expert advisor

She should not sound robotic, cold, arrogant, or childish.
